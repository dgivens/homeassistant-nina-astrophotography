# N.I.N.A. Astrophotography integration — v2.0 design

**Status:** approved design, revised after architecture and domain review, pending implementation plan
**Date:** 2026-09-04 (rev 2)
**Supersedes:** `V2-NOTES.md` on `wip/v2.0`

> **Revision note.** Rev 1 was reviewed for architectural soundness and for
> N.I.N.A. domain correctness. Both reviews landed substantive findings, several
> verified against a live rig and against `ninaAPI` / N.I.N.A. source. §3, §6
> and §7 changed materially; §4, §5, §9 and §11 have edits. Where rev 1 was
> wrong, this document says so rather than quietly correcting it — the errors
> are instructive about which assumptions were unsafe.

---

## 1. Purpose

Bring the integration into line with the N.I.N.A. Advanced API as it exists
today, and with Home Assistant's conventions. Three drivers:

- Endpoint paths, parameters and response fields drifted from the API and were
  never corrected; several entities and services have never worked.
- Every entity hangs off one device, so two rigs cannot be configured side by
  side, and driver metadata sits in entity attributes where Home Assistant does
  not expect it.
- Polling is far more expensive than it needs to be, and the WebSocket stream is
  used only as a hint to re-poll rather than as a data source.

Ships as a single `2.0.0`.

## 2. Decisions

| Decision | Choice |
|---|---|
| API target | ninaAPI **v2** (2.2.15.x), structured so v3 is additive |
| Audience | Solo — no migration machinery; renames are documented, not coded around |
| Quality bar | **Bronze**-conformant, split test suite |
| Reconciliation | `main` is trunk; `wip/v2.0` is a **read-only reference** |
| Release shape | One `2.0.0` |
| Long-running commands | **`Operation` handle in the protocol from day one** (§4.2) |

### 2.1 Why `main` is the trunk

`wip/v2.0` branched from the upstream tip and contains **none** of the 18 fix
branches on `main`. It is two commits — one a 5,937-line blob across 33 files —
with **zero tests**.

| | `main` (1.4.x) | `wip/v2.0` |
|---|---|---|
| Endpoint paths / params | wrong (fixed in 1.4.5) | **correct** — audited, live-validated |
| Error / envelope handling | **correct** | old; ignores `Success: false`, swallows poll errors |
| Entity / device model | flat, single device | **hub + devices, `has_entity_name`, multi-instance** |
| Coverage | ~20 services | **37 services; switch/rotator/dome/flat/AF-history** |
| Tests | **101, green** | zero |

Rebasing the blob is rejected: 16 of its 33 files also changed on `main`, all
conflicts arrive at once, and there are no tests on the v2.0 side to validate a
resolution. Files are lifted only where they cannot conflict (`device.py`,
`helpers.py`, `switch_device.py` are new) or are declarative (`services.yaml`,
`strings.json`).

## 3. Verified findings

All live measurements are from a rig running **Advanced API 2.2.15.2 /
N.I.N.A. 3.2.0.9001**, 2026-09-03/04, mid-session, over Tailscale.

### 3.1 Dead endpoints — mostly resolved in 1.4.5

Nine paths in `api.py` did not exist in the 2.2.15 spec. Seven were fixed in
**1.4.5** (branch `fix/api-endpoint-paths`, 10 commits, 101 tests green),
including one that mattered far more than a dead path:

> **`/equipment/mount/slew` reads RA in degrees; the service takes decimal
> hours.** Fixing only the path would have made the slew start working and send
> the mount **eight hours away, to the wrong side of the meridian, silently** —
> 22.07 is a valid RA read either way. Verified live: `RightAscension: 22.0708`
> alongside `Coordinates.RADegrees: 331.0625`, ratio exactly 15.0000. The
> service contract stays in hours; conversion happens once in the client.

Carried into this release:

| Item | Why it is 2.0.0 work |
|---|---|
| `/image/latest` → `/image/{index}` or `/prepared-image` | response-shape change |
| `/sequence` → `/sequence/json` | different shape entirely (§3.3) |
| 53 dead `ENDPOINT_*` constants in `const.py` | cleanup; paths move into `api/v2/client.py` |
| `camera_capture` ignores exposure time | sends `time`, API reads `duration`; `binning`/`filter_index` bind nothing — service redesign |
| `sequence_load` never loads the sequence | sends `path`, API reads `sequenceName` (a name from `/sequence/list-available`) — service redesign |

**Open:** the slew epoch. The old path name asserted J2000; `/equipment/mount/slew`
says only "the provided coordinates", and the mount reports `Coordinates.Epoch:
'JNOW'`. If the slew is JNOW, there is a residual ~0.36° precession error —
plate-solve-recoverable, but wrong. Resolve from N.I.N.A. source before 2.0.0.

### 3.2 OpenAPI spec: trustworthy for names, **not** for types

Rev 1 concluded the spec was "good enough to generate from" on the strength of a
field-**name** audit. That audit was incomplete in two ways.

Names do match — nine of eleven device schemas field-for-field, with
`CameraInfo` missing `HasBattery` and `MountInfo` missing `CanSlewAltAz`. But
the audit **excluded Dome and FlatDevice** — precisely the two devices §5
creates dynamically — and `DomeInfo` is missing five fields the rig returns
(`Altitude`, `AltitudeDMS`, `AzimuthDMS`, `FollowingType`, `ApplicationFollowing`).

Types are materially wrong:

| Field | Spec | Wire |
|---|---|---|
| `WeatherInfo.CloudCover` | `integer` | `"NaN"` |
| `WeatherInfo.Humidity`, `Pressure` | `integer` | 59.3, 958.5 |
| `WeatherInfo.RainRate`, `SkyBrightness`, `SkyTemperature`, `WindGust` | `string` | numeric |
| `RotatorInfo.Position`, `MechanicalPosition` | `integer` | **335.0736**, 53.86 |
| `DomeInfo.Azimuth` | `integer` | `"NaN"` |
| `MountInfo.TrackingRate` | `object` | `{}` |
| `CameraInfo.Gains` | `array` | `[]` |

The pattern is diagnostic: generated from a single sample, so whatever happened
to be `"NaN"` got typed `string` and whatever happened to be integral got typed
`integer`. `RotatorInfo.Position: integer` truncates 335.0736 in any consumer
that trusts it.

**Consequence:** the §8 drift guard must check **types as well as names**, or it
passes while shipping wrong ones.

Also confirmed: **`TrackingMode` is spelled `'Siderial'` in the spec and
`'Sidereal'` on the wire.** Generating and trusting it would ship a `Literal`
that never matches.

### 3.3 Poll cost — and the endpoint rev 1 never measured

```
/sequence/state             57,234 B   ← 47,879 B earlier the same evening
/profile/show?active=true   14,396 B
/equipment/info              7,245 B
image-history (both calls)      669 B
last-af + flats/status        2,011 B
```

Two corrections to rev 1:

**`/sequence/state` grows all night.** It embeds `SchedulerProgress.ProgressItemList`,
an append-only row per Target Scheduler step — 51 rows by 23:30, +16% payload in
one evening. This is the same compounding failure `V2-NOTES.md` diagnosed for
`/image-history?all=true`, relocated onto a payload 100× larger.

**`/sequence/json` exists and is 6.8× smaller.** Measured **8,429 B**, and it
carries `Status`, `Name`, `Items`, `Conditions`, `Triggers`. The spec explicitly
recommends it:

> `/sequence/json` — "This endpoint is generally advised to use over state since
> it gives more reliable results."
> `/sequence/state` — "Use this endpoint (not json!) as reference for sequence
> **editing**."

`/sequence/state` uses blanket reflection over every public read/write property
of every instruction type (18 names excluded); `/sequence/json` uses a
hand-written per-type map. That is the whole size difference. Neither
`V2-NOTES.md` nor rev 1 considered it.

`/equipment/info` saves only ~7% of bytes over 11 separate `/info` calls. Its
value is **11 round-trips → 1** and an **atomic snapshot** — the 11 separate
calls can return state from 11 different instants.

### 3.4 Event coverage — narrower than rev 1 claimed

68 events documented; every event the rig emitted is documented (65 literal
names + 3 dynamic `TS-*`). But rev 1's replacement table was wrong in four
places, all verified against source and the live rig:

| Endpoint | Event-driven? | Evidence |
|---|---|---|
| `/sequence/state`/`json` | **No** | **244 events overnight, zero `SEQUENCE-*`.** Per-instruction `Status` is a bare `RaisePropertyChanged` for WPF binding — no mediator, nothing subscribable. `SEQUENCE-STARTING` fires *after* the tree resets to `CREATED`, so a refetch on it returns an idle-looking tree. `SEQUENCE-FINISHED` carries no payload. |
| `SEQUENCE-ENTITY-FAILED` | **Not available** | Emitted only by a "Send Error to WebSocket" trigger the user drags into the sequence. This rig's global triggers are Discord / Dew Heater / MQTT — **it can never fire here.** Payload is a display name with no id or index. |
| `/profile/show` | **Switches only** | `ProfileService.ProfileChanged` has one call site — `SelectProfile`. Editing focal length in Options, or `/profile/change-value`, emits nothing. |
| `/equipment/focuser/last-af` | **Success only** | `BroadcastSuccessfulAutoFocusRun` has one call site, after the retry loop succeeds. A failed AF gives `AUTOFOCUS-STARTING` then silence. Worse: the report file is written **per attempt, before the verdict**, and the endpoint returns the newest by creation time — so a rejected run overwrites "last AF" with no success flag. |
| `/flats/status` | **No event exists** | The `FLAT-*` events are flat-*panel hardware* (cover, light, brightness). Nothing reports capture progress. |

What *is* push-driven and reliable: **`*-CONNECTED` / `*-DISCONNECTED` for all
eleven devices**, `SAFETY-CHANGED`, `FILTERWHEEL-CHANGED`, `IMAGE-SAVE`,
`MOUNT-BEFORE-FLIP` / `-AFTER-FLIP`, `DOME-SHUTTER-*`, `FLAT-COVER-*`,
`STACK-UPDATED`, `TS-*`.

**`IMAGE-SAVE` has two shapes.** Live socket carries `ImageStatistics` and no
`Time`; `/event-history` carries `Time` and **no statistics** — verified, all 28
stored copies are exactly `{Event, Time}`. So replay reseeds the **timestamp
only**; frame statistics must come from `/image-history`.

**Three timestamp formats**, two of them naive and indistinguishable by shape:

| Class | Example | Semantics |
|---|---|---|
| mediator events (211) | `2026-09-03T23:26:19.36-05:00` | offset-aware local |
| `TS-*` (32) | `2026-09-04T02:15:32.78` | naive **UTC** |
| log-scraped (1) | `2026-09-03T21:54:26.93` | naive **local** |

The timezone assumption must be keyed on the **event name** — a table in
`api/v2/mapper.py`, not a heuristic.

**`ERROR-*` events are log-file regex scraping.** `ERROR-PLATESOLVE` matches
`^ASTAP - Plate solve failed.` — ASTAP only, which is why this rig sees it.
`ERROR-AF` appears to be dead (its `^`-anchored regex cannot match the line
Serilog actually writes). Build the failure entity — it is cheap and works here —
but document it as solver-specific and best-effort.

**`{DEVICE}-INFO-UPDATED` is dead code.** `SendConsumerEvent` has an
unconditional `return` before its body. Do not plan around it.

**`TS-*` payloads carry a serialization bug:** `"Coordinates": {"RA": [], "Dec":
[], "RADegrees": [] …}` — empty arrays where scalars belong, roughly once per
exposure. The "Send WebSocket Event" instruction also puts a **bare string** in
`Response` with no `Event` key. The parser must survive both.

### 3.5 Failure shapes — the HTTP status is a lie

Rev 1 described three shapes from black-box probing. Source reading shows the
model was incomplete in a way that breaks §7 as written.

`CoreUtility.WriteToResponse` **never assigns `context.Response.StatusCode`** —
the assignment is commented out. So the 404 and 400 probes hit **EmbedIO's
routing and parameter binding, before the handler runs**. Every *handler-level*
outcome is transported as **HTTP 200**, with the real code only in the body:

| Case | HTTP | Body |
|---|---|---|
| unknown path | 404 | EmbedIO HTML — pre-handler |
| malformed param | 400 | EmbedIO HTML — pre-handler |
| `Index out of range` | **200** | `{Success:false, Error:"Index out of range", StatusCode:400}` |
| `Sequencer not initialized` | **200** | `{Success:false, Error:"…", StatusCode:409}` |
| sequence serialization failure | **200** | **empty body — no envelope at all** |

**Consequence:** the taxonomy must key on the **envelope's `StatusCode`**, not
the transport status, for everything except genuine routing failures.

**`"NaN"` is the most common sentinel on this API, and rev 1 omitted it
entirely.** .NET serializes `double.NaN` as a JSON **string**. Live right now:
`Dome.Azimuth`, `Dome.Altitude`, `WeatherData.CloudCover`, `SkyQuality`,
`StarFWHM`. Also reachable on `CameraInfo.CoolerPower` and
`MountInfo.TimeToMeridianFlip`. v1.4.4 already handles it (`sensor.py:44`); the
rev 1 dataclass plan silently dropped that handling. Three weather channels are
permanently `"NaN"` on this rig, and **`weather_abort.yaml` triggers on cloud
cover — that branch can never fire today, and nothing says so.**

**`Success: false` on success is enumerable.** Exactly seven handlers assign
`Success` from a driver boolean, leaving `Error: ""` and `StatusCode: 200`:
`guider/clear-calibration`, `dome/set-follow`, `mount/tracking`, the three
`waitForResult` branches of `mount/slew`, and `framing/determine-rotation`.
That is the test list for §7's discrimination rule.

**No authentication exists** — no security schemes, and the rig answers
unauthenticated. `ConfigEntryAuthFailed` and Silver `reauthentication-flow` are
**not applicable**; recorded as exemptions.

## 4. Architecture

```
custom_components/nina_astrophotography/
├── __init__.py        setup/unload, runtime_data, service registration
├── api/
│   ├── __init__.py    NinaClient + Operation protocols · errors re-export
│   ├── errors.py      taxonomy (§7) — subclasses builtins only
│   ├── models.py      normalized frozen dataclasses  ← THE CONTRACT
│   └── v2/
│       ├── __init__.py  NinaClientV2
│       ├── schema.py    ── GENERATED from OpenAPI, committed ──
│       ├── client.py    envelope, all-GET, paths, StatusCode keying
│       ├── mapper.py    wire → models; sentinels, timezones, quirks
│       ├── operation.py Operation backed by completion events
│       └── events.py    WebSocket firehose + /event-history fold
├── coordinator.py     DataUpdateCoordinator[NinaData]   ← Bronze: common-modules
├── entity.py          NinaEntity base                   ← Bronze: common-modules
├── device.py          hub + via_device registry
├── derive.py          pure, version-independent maths
├── session.py         pure fold: frames + events → SessionStats
├── const.py, config_flow.py, <8 platform modules>
```

`api/v3/` is **not** scaffolded. An empty directory documents an intention; the
protocol is the artifact. Likewise `create_client()` is deferred — there is one
implementation and nothing to dispatch on, so `api/__init__.py` imports
`NinaClientV2` directly. (Relatedly, `config_flow.py:76` currently offers
`vol.In(["v2"])` — a dropdown with one valid choice. It goes.)

| `switch_device.py` (`wip/v2.0`) | **Absorbed into the platforms** (§5). |
| `device.py` (`wip/v2.0`) | Lifted, **with `_INSTANCE_NAMES` moved to `runtime_data`** — a module-level dict keyed by `entry_id` is the exact pattern Bronze `runtime-data` removes, and it leaks on failed unload. |
| `const.py` | Domain, conf keys, enums. The 53 dead `ENDPOINT_*` go. |
| `config_flow.py` | Instance name; API-version dropdown removed; 100% test coverage. |

### 4.1 Three type layers

1. **`v2/schema.py` — generated `TypedDict`s.** `datamodel-codegen
   --output-model-type typing.TypedDict --target-python-version 3.14`. 87
   classes, 1,243 lines, 39 `Literal` enums. TypedDict because the wire data is
   already a dict from `json.loads` — static checking at zero runtime cost.
2. **`v2/client.py`** fetches, unwraps, returns those TypedDicts.
3. **`api/models.py` — hand-written frozen dataclasses**, sized by what entities
   consume, built by `v2/mapper.py`.

**No runtime dependency.** `datamodel-codegen` is a dev tool; output is
committed; `manifest.json` keeps `requirements: []`.

**Generated types are an input, not an oracle** (§3.2). Hence the drift guard,
which checks types as well as names.

**Models must distinguish "never seen" from "present but disconnected"** —
`camera: CameraModel | None` where `None` means never observed, plus
`CameraModel.connected: bool`. §5's dynamic devices and §7's availability levels
both need it from the same snapshot.

**`models.py` is closed to fields no entity consumes.** Enforced by a test that
asserts every model field is referenced by at least one entity descriptor —
about fifteen lines, and it is what stops the layer drifting back toward the
250-field completeness this rejects.

**`v2/mapper.py` is the highest-risk module** — ~250 fields, every quirk,
hand-written, the only place a mistake is unguarded by types on both sides.
Mitigation: one mapping function per model, each fixture-tested.

**The mapper owns all wire quirks**, and rev 1 wrongly split these with
`derive.py`:

- `"NaN"` → `None` as a **blanket rule** over every numeric field, not a
  per-field allowlist
- calibration sentinels `HFR 0` / `Stars −1` → `None`
- `TimeToMeridianFlip` NaN, and the 24 sentinel (§11)
- the three timestamp classes, keyed by event name
- `'Sidereal'`, `UTCDate` having no offset, per-mount `TrackingModes`

If a sentinel reaches `derive.py`, `models.py` carries sentinel values and the
seam is broken on day one — v3 would re-learn every one.

**`derive.py` gets only version-independent maths:** image scale, HFR→arcsec,
progress arithmetic, the flip-warning threshold. The `/sequence/json` walk is
*not* pure — the tree shape is partly a Target Scheduler fact — so the mapper
normalizes it into a `SequenceNode` model and `derive.py` walks that.

### 4.2 `Operation` — long-running commands

v3 returns a `ProcessId` you poll, cancel or await. That is a **semantic**
change; a protocol declaring `slew() -> None` would force `NinaClientV3` to poll
internally, so an HA button press would await a multi-minute slew inside a
service call and v3's cancellation would be unreachable from above the seam.

```python
# api/models.py — version-independent
class OperationState(StrEnum):
    RUNNING = "running"; SUCCEEDED = "succeeded"
    FAILED = "failed";   CANCELLED = "cancelled"

class Operation(Protocol):
    @property
    def state(self) -> OperationState: ...
    async def wait(self, timeout: float | None = None) -> OperationState: ...
    async def cancel(self) -> None: ...   # NinaUnsupportedError under v2
```

`slew`, `capture`, `auto_focus`, `cool_camera`, `park` return `Operation`.

**This pays for itself under v2.** Today `auto_focus()` returns the instant the
API accepts it and nothing correlates `AUTOFOCUS-FINISHED` back to the caller.
`api/v2/operation.py` backs the handle with the matching completion event
(`AUTOFOCUS-FINISHED`, `API-CAPTURE-FINISHED`, `MOUNT-PARKED`); commands with no
completion event return a pre-completed handle. v3 swaps the backing for
`ProcessId` polling and gains a real `cancel()` — additive.

**AF failure needs derived detection** (§3.4): an unmatched `AUTOFOCUS-STARTING`
with no `AUTOFOCUS-FINISHED` inside `AutoFocusTimeoutSeconds` is the only
reliable signal. The v2 `Operation` for `auto_focus` times out on exactly that,
and it also drives `binary_sensor.autofocus_failed`.

**Event subscription is topic-scoped now**, not later: `subscribe(topics:
frozenset[EventTopic], callback)`. v2 ignores `topics` and filters after
receipt; v3 maps them to channels. Otherwise v3 must subscribe to everything and
filter client-side, discarding the feature.

### 4.3 `session.py` — a pure fold, under the coordinator

Rev 1 left session statistics as a stateful store outside the coordinator,
preserving today's two-sources-of-truth problem: `__init__.py:117` writes to the
frame store *and* requests a coordinator refresh, while `frame_stats_sensor.py`
subscribes to the store rather than the coordinator.

**Frames have wire identity and rev 1 ignored it.** Today's code stamps each
frame with a locally-generated `_session_index` and `datetime.now()` — both
properties of *reception*. Both paths carry the real identity:
`/image-history` records and `IMAGE-SAVE`'s `ImageStatistics` each carry `Date`
and `Filename` (and an `Index` the current code discards).

So:

- `session.py` exposes `fold(frames, events) -> SessionStats`, keying frames on
  **`(Date, Filename)`**. Push, poll and replay become the same idempotent
  operation; arrival order stops mattering.
- The session boundary is **derived, not mutated** — filter by the timestamp of
  the most recent `SEQUENCE-STARTING` in the folded set rather than calling
  `reset()`, so a replayed event cannot wipe frames a concurrent poll folded in.
- `SessionStats` is a field on `NinaData`. Entities read it through
  `CoordinatorEntity` like everything else. No listeners in `session.py`.

Without this, a sub pushed by `IMAGE-SAVE` and then returned by the floor poll
counts twice, and a reconnect replaying the backlog double-counts every frame of
the session.

## 5. Entity and device model

The `wip/v2.0` device model stands: hub service device, one child per equipment
type via `via_device`, driver metadata synced into the registry. `DriverInfo`
stays unmapped — though not because it is universally useless: the rotator
returns the ASCOM template default, but the filter wheel returns
`"SDK: 1, 7; FW: 4.0.4"` and the focuser a real driver string. `DriverVersion`
is clean everywhere and is the right `sw_version`.

`wip/v2.0` defines **~203 entities**. Four cuts, each tied to a rule.

**1 — `*_connected` becomes availability. (−10, not −11)**
Silver `entity-unavailable`. For ten devices this is right and nothing is lost —
`unavailable` is observable in automations.

**The safety monitor is the exception.** Under §7 level 2 a disconnected safety
monitor makes `binary_sensor.safety_is_safe` **unavailable**, so a roof-close
automation on `to: "off"` does not fire. Both `SAFETY-DISCONNECTED` and
`SAFETY-CONNECTED` appear in tonight's history, so this is not hypothetical, and
`to: "unavailable"` cannot substitute — it conflates device-disconnected,
N.I.N.A.-unreachable, HA-restarting and coordinator-failed. **Keep
`binary_sensor.safety_monitor_connected`** as `DIAGNOSTIC`, and state in phase 5
that safety and weather blueprints trigger on `to: ['off', 'unavailable',
'unknown']`. It is the only asymmetric-risk entity in the set.

**2 — Equipment devices created dynamically. (Dome −17, FlatDevice −6, conditional)**
Gold `dynamic-devices`. Create on first sight, not at setup — gear is routinely
disconnected at boot, confirmed live. Pair it with
`async_remove_config_entry_device` so a sold dome can be deleted rather than
lingering as ~17 permanently-unavailable entities.

**3 — Read-only mirrors of writable entities. (−14)**

| Drop | Survivor |
|---|---|
| `sensor.rotator_position`, `sensor.rotator_mechanical_position` | the two `number`s |
| `sensor.dome_azimuth` | `number.dome_azimuth` |
| `sensor.camera_usb_limit` | `number.camera_usb_limit` |
| `binary_sensor.camera_cooling_enabled`, `camera_dew_heater_on` | the two `switch`es |
| `binary_sensor.dome_following`, `rotator_reversed` | matching `switch`es |
| `binary_sensor.dome_shutter_open` | `sensor.dome_shutter_status` |
| `binary_sensor.flatdevice_cover_open`, `flatdevice_light_on` | cover switch / `light` |
| `binary_sensor.mount_tracking`, `sensor.mount_tracking_mode` | `select.mount_tracking_rate` |

Behavioural requirement: the survivor's state is the **actual** value, not the
last commanded one.

Three reinstatements from rev 1:

- **`sensor.focuser_position` survives, disabled by default, with
  `state_class: measurement`.** The cut's premise was right — `FocuserInfo.Position`
  is actual, and backlash is applied below it — but `NumberEntity` has no
  `state_class`, so dropping the sensor loses long-term statistics. Focuser
  position against temperature over a night is the standard temp-comp-slope and
  slip diagnostic, and this rig has `TempCompAvailable: false`. The same
  argument does *not* apply to rotator, dome azimuth or USB limit.
- **`sensor.guider_status` survives.** `GuiderInfo.State` is
  `Looping | LostLock | Guiding | Stopped | Calibrating`, and `switch.guider.is_on`
  is `State == "Guiding"`. During `LostLock` the switch reads **off**, so a
  "restart guiding when it stops" automation fires mid-exposure and re-issues
  `/equipment/guider/start`. Worse than doing nothing.
- **`binary_sensor.rotator_synced` survives.** `Position` (sky PA) is only
  meaningful when `Synced` is true; unsynced it degenerates toward
  `MechanicalPosition`. Without it the number is silently untrustworthy after
  any rotator power cycle.

**4 — Collapse the duplicate polled/pushed families. (−8)**
One family fed by both paths (§4.3). Note this fixes the post-restart timestamp
but **not** the statistics — `/event-history`'s `IMAGE-SAVE` carries no
`ImageStatistics`, so stats reseed from `/image-history` (§3.4).

**Livestack — partially reinstated.** It is running on this rig (26
`STACK-UPDATED` overnight). Cut `sensor.livestack_status`,
`binary_sensor.livestack_running` and `switch.livestack`; **add
`image.livestack`** from `/livestack/image/{target}/{filter}`. The accumulating
stack is a materially better dashboard image than the last raw sub.

**Flats — kept, disabled by default.** `/flats/status` only observes flats
started through the API; this rig runs Target Scheduler Flats, so it reads
`{State:"Finished", TotalIterations:-1, CompletedIterations:-1}` straight
through a dawn run — confirmed live. Ship the entities `DIAGNOSTIC` +
`entity_registry_enabled_default=False`, and **poll `/flats/status` only in a
session where a flats service was invoked through the integration.** No event
exists, so there is no cheaper option.

**Screenshot image entity and active-tab select — cut.** N.I.N.A. UI controls.

**The N.I.N.A. switch device — enabled by default, with two corrections.**
Channels become entities like any other equipment:

- a channel where `Max − Min == StepSize` is **binary** → `switch` platform, not
  `number`
- read **`Value`**, not `TargetValue` — the same actual-not-commanded rule as
  cut 3, and this endpoint exposes both

On this rig the switch device is an HA→N.I.N.A. bridge exposing two Kasa outlets,
so the entities duplicate ones that already exist natively. That is accepted and
harmless — the same entity appearing through two integrations is ordinary — and
the normal case is a real ASCOM switch (a Pegasus Pocket Powerbox and its
outlets, dew heaters and voltage/current channels), which is what the default
should serve.

## 6. Data flow: push where it works, poll where it doesn't

Rev 1 over-claimed. §3.4 shows the sequence, profile, last-af and flats tiers
cannot be purely event-driven. Revised:

| Tier | Interval | Calls | Bytes |
|---|---|---|---|
| Fast | 10 s | `/equipment/info`, `/image-history?count=true` | 7,316 B |
| Sequence | 30 s while any node reads `RUNNING`, else 5 min | **`/sequence/json`** | 8,429 B |
| Event-driven | on `PROFILE-*`, `AUTOFOCUS-FINISHED`, `IMAGE-SAVE` | `/profile/show`, `/last-af`, `/image-history` | 0 at rest |
| Conditional | only after a flats service call | `/flats/status` | 0 normally |
| Floor | 5 min | the event-driven set | amortised |
| Setup only | — | `/version`, `/version/nina`, `/application-start` | — |

```
fast       7,316 B @ 10 s  =  43,896 B/min
sequence   8,429 B @ 30 s  =  16,858 B/min
                              ──────────
                              60,754 B/min ≈ 3.6 MB/h ≈ 36 MB / 10 h night

current                       82,606 B × 6/min ≈ 297 MB / night    → ~8×
```

Rev 1 claimed 11×. **~8× is the honest figure**, and it depends on
`/sequence/json`; on `/sequence/state` it would have been ~2×, degrading all
night as the payload grows.

**Do not refetch on `TS-TARGETSTART`.** It fires once per *exposure* — 27 in 3.8
hours — and its payload already carries `TargetName`, `ProjectName`, `Rotation`
and `TargetEndTime`, which is everything `sensor.sequence_target` needs.
Refetching on it was most of rev 1's underestimate. Debounce any sequence
refetch to ≤1 per 30 s.

**The push path calls `async_set_updated_data`, not `async_request_refresh`.**
Rev 1 never said so, and the natural implementation against a
`DataUpdateCoordinator` is a refresh request — which is exactly the
socket-as-a-hint design §1 identifies as the problem. This one line is what
makes push-first real.

**Reconnect and setup.** Replay `/event-history` and fold in what was missed.
`WebSocketV2.Events` is an unbounded `static` list with no cap, no eviction and
no `Clear()`, and the endpoint has no `since`, `limit` or pagination — it grows
monotonically for the life of the N.I.N.A. process (27.7 KB / 233 events at
23:30). So the client **dedupes against a high-water mark by `(Event, Time)`**
rather than folding blindly, and the fold is capped.

**Coordinator.** One `DataUpdateCoordinator[NinaData]`; `NinaData` is a frozen
dataclass holding the normalized snapshot including `SessionStats`.

**`PARALLEL_UPDATES`** — `0` on read-only platforms, `1` on command platforms.
Note this constrains *entity* calls only: the 37 services are unaffected, so a
script calling three `nina.mount_*` services still fires concurrently. If
serialising at the mount matters, that needs a per-entry lock in the client.

**Image scale needs no profile special-case.** Rev 1 built one for focal length
being absent until the first `PROFILE-CHANGED`. Unnecessary — `/image-history`
frames carry `FocalLength` and `TelescopeName` **per frame**, and
`CameraInfo.PixelSize` is in the fast tier. Deriving from the frame's own focal
length is simpler *and* more correct: it is the FL in force for that frame
rather than the current profile's.

**Nothing safety-related is on the floor.** Safety monitor, all weather
channels, dome shutter, mount park state and camera temperature are in the 10 s
fast tier, with `SAFETY-CHANGED` on top. The floor covers sequence, profile,
last-af, flats and image-history only.

**Sequence progress:** per-instruction `Status` has no event, so the 30 s poll
while `RUNNING` is the freshness bound. `/sequence/state`'s
`SchedulerProgress.CurrentRow.ItemName` (`Slew`, `BeforeTarget`, `SwitchFilter`,
`TakeExposure`) is the best "what is the rig doing now" signal in the API and is
strictly better than target-from-last-light-frame — but it lives on the 57 KB
endpoint. Deferred: revisit if `/sequence/json` proves insufficient.

**Container `Iterations` is *completed* iterations** — `0` on a running
container, `42` on a finished loop. Almost certainly the root of the
progress-never-reaches-100% bug. `derive.py` must not use it as a numerator.

## 7. Errors and availability

`api/errors.py` subclasses **builtins only** — never `HomeAssistantError` — so
the fast suite stays HA-free. Mapping to HA exceptions happens in `__init__.py`
and `coordinator.py`.

| Exception | Raised when | Retryable |
|---|---|---|
| `NinaConnectionError` | socket refused, DNS, timeout | yes |
| `NinaUnavailableError` | envelope 5xx, or N.I.N.A. mid-boot | yes |
| `NinaEndpointError` | capability not served by this build | **no** |
| `NinaRequestError` | malformed request (pre-handler 4xx, HTML body) | **no** |
| `NinaCommandError` | envelope `StatusCode` 4xx/5xx with a real `Error` | depends |
| `NinaNoDataError` | `Index out of range`, `Sequencer not initialized` (409) | not an error |
| `NinaUnsupportedError` | `Operation.cancel()` under v2 | n/a |

**Definitions are semantic, not HTTP.** Rev 1 defined `NinaEndpointError` as
"404/405/501", a v2 wire fact that also fails against §3.5 — handler-level
outcomes never reach the transport status. The status-code mapping is documented
**inside `v2/client.py`**, which keys on the **envelope's** `StatusCode` except
for genuine EmbedIO routing failures. `v2/client.py` must also handle a
**zero-length 200**.

The `Success: false` discrimination stays in `v2/client.py`: `Success` alone
cannot be keyed on, because seven handlers assign it from a driver boolean and
answer `Success: false, Error: "", StatusCode: 200` on success (§3.5 names them).

**Mapping to Home Assistant**

- **Setup** (Bronze `test-before-setup`): `NinaEndpointError` → `ConfigEntryError`;
  connection/unavailable → `ConfigEntryNotReady`.
- **Coordinator**: retryable → `UpdateFailed`; `NinaRequestError` /
  `NinaEndpointError` → log once, keep the previous snapshot.
- **Actions** (Silver `action-exceptions`): `ServiceValidationError` for bad
  input, `HomeAssistantError` for genuine failure — platform actions included.

**Availability, three levels**

1. Cannot reach N.I.N.A. → coordinator fails → all entities unavailable.
2. Device `Connected: false`, or `*-DISCONNECTED` arrived → that device's
   entities unavailable. **Exception: the safety monitor is fail-safe** (§5).
3. Reachable and connected but the value is missing or sentinel — `"NaN"`,
   `HFR 0`, `Stars −1`, `Index out of range`, `Sequencer not initialized`, the
   meridian 24 sentinel → **`unknown`**, not unavailable.

**`log-when-unavailable`** (Silver): transition logged once at `warning`,
recovery once at `info`. `poll_all`'s `except: results[key] = {}` disappears —
that swallow produced the publishes-defaults bug.

## 9. Phasing

A `v2` branch off `main`; each phase a PR into it; `v2` → `main` and tag `2.0.0`.

**Rev 1 stated the ordering constraint and then applied it to the wrong module.**
Platforms do not touch `api.py` — they touch `coordinator.data`. Rewriting the
coordinator in phase 2 breaks all eight platforms at once, which is the exact
failure the phasing exists to prevent. The compatibility contract:

> `NinaData` carries a `legacy: dict[str, Any]` field holding the raw poll
> snapshot in today's `{subsystem: {"Response": …}}` shape, populated by
> `v2/mapper.py` alongside the typed fields. Unmigrated platforms read
> `coordinator.data.legacy`; each phase-3 PR moves one platform onto typed
> fields; the last one deletes the field along with `api.py`.
>
> The `legacy` dict must be built from a **full poll of the old endpoint set**
> for as long as it exists. **Phase 2 keeps the old fetch topology; the last
> phase-3 PR flips to §6's tiering.** Otherwise `/image-history?count=true`
> returns a scalar where `sensor.py:_latest_stat` expects a list, and the
> frame-derived sensors read `unknown` for the whole of phase 3 with no test
> failing.

| Phase | Content | Size |
|---|---|---|
| **0 · Scaffolding** | Split harness, `pytest-homeassistant-custom-component`, CI (pytest + hassfest + HACS), `test_no_ha_import.py`. `scripts/capture_fixtures.py` + first corpus. `datamodel-codegen` → `api/v2/schema.py` + drift test. **No behaviour change**; 101 tests stay green. | S–M |
| **1 · Seam + one vertical slice** | `api/` package, `derive.py`, `session.py`, `FakeNinaClient`. Then migrate **`light.py`** (103 lines, one entity) end-to-end through client → mapper → models → coordinator → entity. | L |
| **2a · Coordinator** | `coordinator.py`, `entity.py`, `runtime_data`, `NinaData` with `legacy`. **Old fetch topology, old device model.** Nothing else moves. | M |
| **2b · Devices + push-first** | `device.py` (with `_INSTANCE_NAMES` → `runtime_data`), `api/v2/events.py`, `/event-history` replay, config-flow instance name. **This is where entity ids change.** | L |
| **3 · Platform migration** | `binary_sensor.py` **first**, then number/select/switch/button/image, then `sensor.py` split into **3a** (onto models), **3b** (frame-stats merge + cut 4 + session), **3c** (switch-device channels). Last PR flips the fetch topology and deletes `api.py`. | **XL** |
| **4 · Services** | 37 → trimmed, device targeting, `action-exceptions`, `Operation`-aware handlers. | M |
| **5 · Blueprints & cards** | Entity selectors; meridian blueprint on `MOUNT-BEFORE-FLIP` (§11); safety/weather triggers include `unavailable`/`unknown`; five cards updated. | M |
| **6 · Release** | README, CHANGELOG, `quality_scale.yaml`, manifest, `hacs.json` min-HA bump from `2024.1.0`. Tag `2.0.0`. | S–M |

**Why `binary_sensor.py` first, not `sensor.py`:** it loses 10 `*_connected`
plus ~9 mirrors out of 44, making it the cleanest demonstration that the
snapshot diff really is the rename mapping — on a platform where a mistake is
cheap. `sensor.py` is larger than the other seven combined and carries the three
highest-risk changes, hence the 3a/3b/3c split.

**Why phase 1 ends with a vertical slice:** otherwise the question that actually
matters — does `NinaData`'s shape fit what entities need? — goes unanswered
until phase 3, across eight PRs, with 167 entities already depending on it.

**Note:** `_get_client()` returns the first entry's client until phase 4. A
second rig configured between 2b and 4 would send every service to rig #1.
Harmless because phases are PRs, not releases — but phase 2b is not "multi-rig
works".

`wip/v2.0` stays read-only through phase 5; delete after 2.0.0.

**Planning granularity.** Phases 0–2b plan together; **phase 3 warrants its own
plan**; phases 4–6 together. Three implementation plans against this design.

## 11. Meridian flip — resolved

Rev 1 listed a ~15-minute disagreement between `TimeToMeridianFlip` and
`HoursToMeridianString` as unresolved. **They never disagreed** — they measure
different things:

```
HoursToMeridian    = (RA_JNOW − LST) mod 12
TimeToMeridianFlip = HoursToMeridian + MaxMinutesAfterMeridian
                     [+12 h when UseSideOfPier and already flipped]
```

Verified live: LST 21.021944, RA 22.071111 → `(RA−LST) mod 12 = 01:02:57`,
matching `HoursToMeridianString` **to the second**; `TimeToMeridianFlip −
HoursToMeridian = 15.00 min`, exactly the profile's `MaxMinutesAfterMeridian: 15`.
`MinutesAfterMeridian` and `PauseTimeBeforeMeridian` appear in neither formula.

**Three consequences:**

1. **Use `TimeToMeridianFlip`** — it is what `MeridianFlipTrigger` consumes. But
   the flip fires when it reaches **(Max − Min)**, i.e. 10 minutes here, **not
   zero**. `meridian_flip_warning.yaml`'s `below: 10` therefore warns *at* the
   flip. The correct threshold is `warning_minutes + (Max − Min)` — and since
   both are per-profile, **a bare numeric threshold is not portable between
   rigs**. Phase 5 uses `MOUNT-BEFORE-FLIP` instead.
2. **The 24 sentinel is misattributed.** It is returned when `TrackingEnabled ==
   false` — parked, homed, *or simply tracking off* — not when "idle". And
   **12 h is legitimate**, meaning "just flipped" (the `UseSideOfPier` branch),
   so a rule like "≥12 → unknown" would be wrong.
3. **A third value exists:** `double.NaN` when the mount object is null (§3.5).

The `Meridian Flip_Trigger` node inside the sequence carries its **own**
`MinutesAfterMeridian` / `MaxMinutesAfterMeridian`, independent of the profile's.
They match here, but prefer the trigger's when present.
