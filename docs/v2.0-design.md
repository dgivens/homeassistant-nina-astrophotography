# N.I.N.A. Astrophotography integration — v2.0 design

**Status:** approved design, pending implementation plan
**Date:** 2026-09-03
**Supersedes:** `V2-NOTES.md` on `wip/v2.0` (carried forward and corrected below)

---

## 1. Purpose

Bring the integration into line with the N.I.N.A. Advanced API as it exists
today, and with Home Assistant's conventions for integrations. Three things
drive the work:

- Endpoint paths, parameters and response fields drifted from the API and were
  never corrected; several entities and services have never worked.
- Every entity hangs off one device, so two rigs cannot be configured side by
  side, and driver metadata sits in entity attributes where Home Assistant
  does not expect it.
- Polling is far more expensive than it needs to be, and the WebSocket event
  stream — which can supply most of the same data — is used only as a hint to
  re-poll.

The release lands as a single `2.0.0`.

## 2. Decisions taken

| Decision | Choice | Consequence |
|---|---|---|
| API target | ninaAPI **v2** (2.2.15.x), structured so v3 is additive | Client is versioned behind a protocol; v3 is a new package, not a rewrite |
| Audience | Solo — no external users to protect | No migration machinery; entity renames are documented, not coded around |
| Quality bar | **Bronze**-conformant, split test suite | 100% config-flow coverage; no global 95% gate |
| Reconciliation | `main` is trunk; `wip/v2.0` is a **read-only reference** | Never merged, never rebased; deleted after 2.0.0 |
| Release shape | One `2.0.0` | Phases are PRs into a `v2` branch, not releases |

### 2.1 Why `main` is the trunk

Neither branch dominates. `wip/v2.0` branched from `505e12e` (the upstream tip)
and contains **none** of the 18 fix branches merged into `main`. It is two
commits, one of which is a single 5,937-line blob across 33 files, and it has
**zero tests**.

| | `main` (1.4.4) | `wip/v2.0` |
|---|---|---|
| Endpoint paths / params | wrong (9 dead paths) | **correct** — audited against the spec, live-validated |
| Error and envelope handling | **correct** — `NinaEndpointError`, envelope discrimination | old; ignores `Success: false`, swallows poll exceptions |
| Entity / device model | flat, single device | **hub + 11 devices, `has_entity_name`, multi-instance** |
| Coverage | ~20 services | **37 services; switch/rotator/dome/flat/AF-history** |
| Tests | **69, green** | zero |
| Manifest URLs | correct | regressed to upstream |

Rebasing the blob is rejected: 16 of its 33 files also changed on `main`, every
conflict arrives at once, and there are no tests on the v2.0 side to validate a
resolution. Files are lifted wholesale only where they cannot conflict
(`device.py`, `helpers.py`, `switch_device.py` are new files) or are purely
declarative (`services.yaml`, `strings.json`).

The chosen v3-seam design supersedes both branches' `api.py` regardless. What
survives is `main`'s **error semantics** and `wip/v2.0`'s **endpoint knowledge**
— control flow and data respectively, which are complementary.

## 3. Verified findings

All measurements below are from a live rig running **Advanced API 2.2.15.2 /
N.I.N.A. 3.2.0.9001**, reached over Tailscale, on 2026-09-03.

### 3.1 Nine dead endpoints in 1.4.4

| `api.py` calls | Spec has |
|---|---|
| `/equipment/camera/abort` | `/equipment/camera/abort-exposure` |
| `/equipment/guider/start-guiding` (param `forceCalibration`) | `/equipment/guider/start` (param `calibrate`) |
| `/equipment/guider/stop-guiding` | `/equipment/guider/stop` |
| `/equipment/guider/dither` | **nothing** — no dither endpoint exists |
| `/equipment/mount/find-home` | `/equipment/mount/home` |
| `/equipment/mount/slew-to-coordinates-j2000` | `/equipment/mount/slew` (ra/dec in **degrees**) |
| `/equipment/flatdevice/toggle-light` | `/equipment/flatdevice/set-light` |
| `/image/latest` | `/image/{index}` |
| `/sequence` | `/sequence/state` (different response shape) |

`get_image_bytes` also sends `useAutoStretch`, which is not a parameter on
`/image/{index}`; the real one is `autoPrepare`. All 53 `ENDPOINT_*` constants
in `const.py` are dead — defined, referenced nowhere else, and many wrong
(`/equipment/telescope/*` does not exist).

*Being handled separately as a `1.4.5` hotfix, except `/image/latest`,
`/sequence` and the dead constants, which belong to this release.*

### 3.2 OpenAPI spec quality — good enough to generate from

Nine of eleven device schemas match the live payload **field for field**:

```
device           spec  rig  drift
Camera             61   62  rig-only=['HasBattery']
Mount              50   51  rig-only=['CanSlewAltAz']
FilterWheel        11   11  —
Focuser            15   15  —
Guider             15   15  —
Rotator            15   15  —
SafetyMonitor       9    9  —
Switch             10   10  —
WeatherData        22   22  —
```

But the spec **is** drifted, in three known ways, one of them dangerous:

- `CameraInfo` missing `HasBattery`
- `MountInfo` missing `CanSlewAltAz`
- **`TrackingMode` enum spelled `'Siderial'` in the spec; the wire says
  `'Sidereal'`.** Generating and trusting this would ship a `Literal` that
  never matches.

Only 42 of 157 `200` responses reference a schema; the other 115 are inline
one-offs. Generation is valuable for the 19 component schemas and worthless for
the rest.

### 3.3 Poll cost is not where `V2-NOTES.md` thought

```
/sequence/state             47,879 B   66%
/profile/show?active=true   14,396 B   20%
/equipment/info              7,245 B   10%
image-history (both calls)      669 B    0.9%
last-af + flats/status        2,011 B
──────────────────────────────────────
total, current design       82,606 B over 20 calls
  → ~29.7 MB/h → ~297 MB per 10-hour night at the 10 s default
```

`V2-NOTES.md` optimised `image-history`, which is **0.9%** of the cost.
`/equipment/info` (new in 2.2.15.0) saves only ~7% of bytes over 11 separate
`/info` calls — its real value is **11 round-trips → 1** and an **atomic
snapshot**, since the 11 separate calls can return state from 11 different
instants.

### 3.4 The event stream can replace the expensive polls

The AsyncAPI spec documents **68 events**, and every event the rig emitted in a
night (192 events, 37 distinct) is documented — no undocumented drift.

| Event | Replaces |
|---|---|
| `PROFILE-CHANGED` / `-ADDED` / `-REMOVED` | polling `/profile/show` — 14,396 B |
| `SEQUENCE-STARTING` / `-FINISHED` / `-ENTITY-FAILED`, `IMAGE-SAVE`, `TS-*` | polling `/sequence/state` — 47,879 B |
| `AUTOFOCUS-FINISHED` | polling `/equipment/focuser/last-af` |
| `*-CONNECTED` / `*-DISCONNECTED` (all 11 devices) | availability and device discovery |

`/event-history` returns the session backlog, which supplies both startup
seeding and post-reconnect catch-up.

Also confirmed live: `UTCDate` carries **no timezone offset** despite being
UTC; this mount reports `TrackingModes: ['Sidereal','Lunar','Solar','Stopped']`
with **no `King`**, so tracking options must come from the mount rather than a
hardcoded list; `GUIDER-DITHER` fires as an event even though no dither
endpoint exists; the rig runs **Target Scheduler** (`TS-*` events), confirming
the sequence tree only names the scheduler's own container.

### 3.5 Three distinct failure shapes

| Probe | HTTP | Body | Meaning |
|---|---|---|---|
| unknown path | 404 | EmbedIO HTML | not served — permanent |
| `image-history?index=9999` | **200** | `{Success:false, Error:"Index out of range", StatusCode:400}` | envelope failure |
| `image-history?index=notanumber` | 400 | EmbedIO HTML | malformed request — permanent |

The third is unhandled today: `_PATH_NOT_SERVED = (404, 405, 501)` treats 400 as
transient, so a malformed request retries forever. `Index out of range` is also
what `/image-history` answers **every night before the first sub** — that is
"no data yet", not a failure.

**No authentication exists.** The spec defines no security schemes and the rig
answers unauthenticated, so `ConfigEntryAuthFailed` and the Silver
`reauthentication-flow` rule are **not applicable** and are recorded as
exemptions.

## 4. Architecture

```
custom_components/nina_astrophotography/
├── __init__.py        setup/unload, runtime_data, service registration
├── api/
│   ├── __init__.py    NinaClient protocol · create_client() · re-exports
│   ├── errors.py      exception taxonomy (§7)
│   ├── models.py      normalized frozen dataclasses  ← THE CONTRACT
│   ├── v2/
│   │   ├── __init__.py  NinaClientV2
│   │   ├── schema.py    ── GENERATED from OpenAPI, committed ──
│   │   ├── client.py    envelope unwrap, all-GET, endpoint paths
│   │   ├── mapper.py    schema.TypedDict → models.dataclass
│   │   └── events.py    WebSocket: single firehose
│   └── v3/              (later — same five files, different wire)
├── coordinator.py     DataUpdateCoordinator[NinaData]   ← Bronze: common-modules
├── entity.py          NinaEntity base                   ← Bronze: common-modules
├── device.py          hub + via_device registry
├── derive.py          pure computations
├── session.py         frame/session statistics accumulator
├── const.py, config_flow.py, <8 platform modules>
```

### 4.0 Disposition of every existing module

Nothing is left unaccounted for:

| Existing module | Disposition |
|---|---|
| `api.py` (main, 419) | **Deleted.** Error semantics → `api/v2/client.py`; endpoint knowledge from `wip/v2.0` → same. Removed when the last platform migrates (phase 3). |
| `coordinator.py` (39) | Rewritten — `DataUpdateCoordinator[NinaData]`, push-first (§6). |
| `websocket.py` (232) | **Moves into the seam** as `api/v2/events.py`; v3 changes the event protocol. |
| `frame_statistics.py` (392) | Becomes **`session.py`** — the stateful accumulator for session totals, rolling averages and per-filter counts. Now fed by **both** `IMAGE-SAVE` and the poll (§5 cut 4), not push alone, which is what fixes the post-restart gap. Its pure computations move to `derive.py`. |
| `frame_stats_sensor.py` (370) | **Merged into `sensor.py`.** Its 25 descriptors were a separate platform module only because they had a separate data source; once one family is fed by both paths there is no reason for a second module. 8 of the 25 are dropped as duplicates. |
| `helpers.py` (`wip/v2.0`, 376) | **Split, not lifted.** Pure computations → `derive.py`; wire-shape quirks (`safe()` dict-digging, `'Sidereal'`, `UTCDate` offset, per-mount `TrackingModes`) → `api/v2/mapper.py`. The `safe()` idiom disappears entirely — nothing above the seam sees a dict. |
| `switch_device.py` (`wip/v2.0`, 165) | **Absorbed into the platforms.** Its job is discovering the N.I.N.A. switch device's channels and creating a sensor per read-only channel and a number per writable one; that is ordinary dynamic entity creation and belongs in `sensor.py` / `number.py` alongside every other descriptor. |
| `device.py` (`wip/v2.0`, 219) | **Lifted wholesale** — new file, no conflict. |
| `const.py` (192) | Keeps domain, conf keys and enums. The 53 dead `ENDPOINT_*` constants are deleted; paths live in `api/v2/client.py`. |
| `config_flow.py` (118) | Extended with the instance name (phase 2); gains 100% test coverage. |
| 8 platform modules | Migrated one per PR in phase 3. |

**The seam rule.** `errors.py`, `models.py` and the protocol in `__init__.py`
are version-independent and stay at `api/` level. *Everything* that knows a
wire format lives under `api/<version>/`. Nothing above `api/` imports from
`api/v2/`; only `create_client()` does, and only to pick an implementation. No
raw dicts cross the boundary — today's `safe(data, "camera", "Response")`
dict-digging disappears.

**`websocket.py` moves into the seam** as `api/v2/events.py`. v3 replaces the
single firehose with per-client channel subscriptions, so the event transport
is version-specific too. What stays shared is the normalized event type in
`models.py`.

### 4.1 Three type layers

1. **`v2/schema.py` — generated `TypedDict`s.** `datamodel-codegen
   --output-model-type typing.TypedDict --target-python-version 3.14`. 87
   classes, 1,243 lines, 39 `Literal` enums, none hand-maintained. TypedDict
   rather than dataclass because the wire data is already a dict out of
   `json.loads` — static checking at zero runtime cost and zero construction
   overhead.
2. **`v2/client.py`** fetches, unwraps the envelope, returns those TypedDicts.
3. **`api/models.py` — hand-written frozen dataclasses**, normalized and sized
   by what entities actually consume, built by `v2/mapper.py`.

Modelling all ~250 device fields by hand is the completeness-for-its-own-sake
this design rejects. Generated wire types are free; normalized models are
sized by consumption.

**No runtime dependency.** `datamodel-codegen` is a dev tool and its output is
committed. `manifest.json` keeps `requirements: []`.

**Generated types are an input, not an oracle.** Three drifts were found in
twenty minutes and one would have silently broken tracking. Codegen therefore
ships with a mandatory **drift test** (§8).

**`derive.py`** holds the pure computations — image scale, HFR→arcsec, the
`/sequence/state` tree walk, sequence progress, target-from-last-light-frame,
calibration sentinel mapping, the meridian idle sentinel, the `UTCDate`
timezone fix. This is where the bugs historically lived, and being pure it goes
in the millisecond test suite.

**`v2/mapper.py`** is where v2-specific quirks are normalized away — the
`'Sidereal'` spelling, `UTCDate` having no offset, `TrackingModes` being
per-mount. They must not leak into `models.py` or they will be re-learned in
v3.

## 5. Entity and device model

The device model from `wip/v2.0` stands: a hub service device with one child
per equipment type linked by `via_device`, driver metadata (`model`,
`model_id`, `sw_version`) synced into the device registry from polls, and
`DriverInfo` deliberately unmapped because several ASCOM drivers return the
template default.

`wip/v2.0` defines **~203 entities**. Four cuts, each backed by a quality-scale
rule rather than taste.

**1 — `*_connected` becomes availability. (−11)**
The Silver `entity-unavailable` rule says a device we cannot reach should make
its entities unavailable, not publish `off` on a side-channel sensor while the
rest report stale values. `unavailable` is fully observable in automations, so
nothing is lost.

**2 — Equipment devices are created dynamically. (Dome −17, FlatDevice −6, conditional)**
Create a device the first time equipment is observed present; keep it
thereafter. Gold `dynamic-devices`. Creation-on-first-sight rather than
at-setup matters because gear is routinely disconnected when Home Assistant
boots — confirmed on the rig, where Dome and FlatDevice were disconnected while
the other nine were live.

**3 — Read-only mirrors of writable entities. (−16)**

| Drop | Survivor |
|---|---|
| `sensor.focuser_position` | `number.focuser_position` |
| `sensor.rotator_position`, `sensor.rotator_mechanical_position` | the two `number`s |
| `sensor.dome_azimuth` | `number.dome_azimuth` |
| `sensor.camera_usb_limit` | `number.camera_usb_limit` |
| `binary_sensor.camera_cooling_enabled`, `camera_dew_heater_on` | the two `switch`es |
| `binary_sensor.dome_following`, `rotator_reversed`, `guider_is_guiding`, `livestack_running` | matching `switch`es |
| `binary_sensor.dome_shutter_open` | `sensor.dome_shutter_status` |
| `binary_sensor.flatdevice_cover_open`, `flatdevice_light_on` | cover switch / `light` |
| `binary_sensor.mount_tracking`, `sensor.mount_tracking_mode` | `select.mount_tracking_rate` |

This carries a **behavioural requirement**, not just deletions: the survivor's
state must be the *actual* value, not the last commanded one.
`number.focuser_position` reads 14,200 while a move to 15,000 is in flight.
That is how Home Assistant defines number/switch/select entities, and it is why
one entity suffices.

**4 — Collapse the duplicate polled/pushed families. (−8)**
`frame_last_hfr`/`image_last_hfr`, `frame_last_stars`/`image_last_star_count`,
`frame_last_mean_adu`, `frame_last_median_adu`, `frame_last_exposure`,
`frame_last_filter`, `frame_session_count`/`image_count`, and
`frame_last_target`/`sequence_target_name`. Keep **one** family fed by **both**
paths: `IMAGE-SAVE` updates it instantly, the poll seeds it at startup and
reconciles. This also resolves the `V2-NOTES.md` "capture time is `unknown`
after a restart" item as a side effect.

**Named cuts:** `livestack` (3, of which `livestack_running` is already counted
under cut 3 — net **2**), the `Screenshot` image entity and active-tab select
(**2**) — N.I.N.A. UI controls, not observatory state.

**Arithmetic**

```
baseline                                203   (88 sensor · 44 binary_sensor · 28 button
                                               · 25 frame-stats · 9 switch · 6 number
                                               · 1 light · 2 image)
                                              NOTE: the select platform is not enumerated
                                              here, so the baseline is a floor, not exact.
  − *_connected → availability            11
  − read-only mirrors                     16
  − duplicate polled/pushed family         8
  − livestack (net of overlap)              2
  − screenshot + active-tab select          2
                                        ─────
                                    ≈   164
```

A further **~23** (Dome 17, FlatDevice 6) appear only if that hardware exists,
so a rig like the test rig sees roughly **140**. Of the 164, the long tail
below ships disabled by default, so a fresh install surfaces materially fewer.

**The long tail ships disabled, not deleted.** `mount_equatorial_system`,
`mount_guide_rate_ra/dec`, `camera_bit_depth`, `weather_average_period`,
`frame_sparkline_data` and similar stay defined with
`entity_registry_enabled_default=False` under `EntityCategory.DIAGNOSTIC` (Gold
`entity-disabled-by-default`). Beyond the four rules above the cut line is
taste; this makes taste a runtime toggle rather than a design argument.

**Tracking options come from the mount.** `select.mount_tracking_rate` reads
its options from `MountInfo.TrackingModes`, not a hardcoded list — this mount
offers four modes and has no `King`.

## 6. Data flow: push-first, poll as a floor

Today the WebSocket is a hint that triggers a full re-poll. It becomes the
primary data path; polling becomes a safety net.

| Tier | Interval | Calls | Bytes |
|---|---|---|---|
| Fast | 10 s (configurable) | `/equipment/info`, `/image-history?count=true` | **7,316 B** |
| Event-driven | on the §3.4 events | `/sequence/state`, `/profile/show`, `/last-af`, `/image-history`, `/flats/status` | 0 at rest |
| Floor | 5 min | the event-driven set, as a missed-event backstop | amortised |
| Once at setup | — | `/version`, `/version/nina`, `/application-start` | — |

```
current   82,606 B × 6/min ≈ 29.7 MB/h ≈ 297 MB / 10 h night
proposed   7,316 B × 6/min ≈  2.6 MB/h ≈  26 MB / 10 h night   (~11×)
```

Event-driven refetches add roughly 2 MB across a night at the observed event
rate.

**Reliability.** A push-first design fails if the socket drops silently.
Therefore: reconnect with backoff; **on every reconnect, replay
`/event-history` and fold in what was missed**; keep the 5-minute floor so a
permanently wedged socket degrades to today's behaviour rather than to stale
state. The same replay runs at **setup**, which is what actually fixes
"capture time is `unknown` after a restart".

**Coordinator.** One `DataUpdateCoordinator[NinaData]` where `NinaData` is a
frozen dataclass from `api/models.py` holding the normalized snapshot.
Entities are `CoordinatorEntity` subclasses off `entity.py` reading typed
attributes.

**`PARALLEL_UPDATES`** — `0` on read-only platforms (sensor, binary_sensor,
image) since the coordinator fetches; `1` on command platforms (button, switch,
number, select, light) so a dashboard full of buttons cannot fire concurrent
commands at a mount.

**Polling interval.** 10 s stays the default and stays configurable. With the
fast tier at 7 KB it costs ~26 MB/night, so adaptive polling is complexity for
a problem this removes.

**Consequence:** `sensor.image_scale` and `sensor.last_image_hfr_arcsec` depend
on focal length, which now arrives via `PROFILE-CHANGED` rather than every
poll. `derive.py` must handle focal length being absent until the first profile
fetch completes.

## 7. Errors and availability

Taxonomy in `api/errors.py`, above the seam so v3 raises the same types:

| Exception | Raised when | Retryable |
|---|---|---|
| `NinaConnectionError` | socket refused, DNS, timeout | yes |
| `NinaUnavailableError` | 5xx, or N.I.N.A. answering unhappily mid-boot | yes |
| `NinaEndpointError` | 404/405/501 — not served by this build | **no** |
| `NinaRequestError` | 4xx with an HTML body — we sent something malformed | **no** *(new)* |
| `NinaCommandError` | HTTP 200, `Success: false` with a real `Error` + 4xx/5xx `StatusCode` | depends |
| `NinaNoDataError` | `Success: false` meaning "nothing yet" | not an error |

The `Success: false` discrimination lives in **`api/v2/client.py` only**.
`Success` alone cannot be keyed on: some handlers assign it straight from a
driver return value, so a *successful* tracking change answers `Success: false`
with an empty `Error` and code 200. Genuine failures come from
`CreateErrorTable` and always carry both a message and a 4xx/5xx code. v3
removes the envelope entirely, which is why this belongs below the seam.

**Mapping to Home Assistant**

- **Setup** (Bronze `test-before-setup`): `NinaEndpointError` →
  `ConfigEntryError`; `NinaConnectionError` / `NinaUnavailableError` →
  `ConfigEntryNotReady`.
- **Coordinator**: retryable → `UpdateFailed`; `NinaRequestError` /
  `NinaEndpointError` → log once at error, keep the previous snapshot.
- **Actions** (Silver `action-exceptions`): `ServiceValidationError` for bad
  input, `HomeAssistantError` for genuine failure. Applies to platform actions
  too, so `switch.turn_on` and `number.set_value` raise rather than
  log-and-return.

**Availability, three levels**

1. Cannot reach N.I.N.A. → coordinator fails → **all entities unavailable**.
2. Device reports `Connected: false`, or its `*-DISCONNECTED` event arrived →
   **that device's entities unavailable**.
3. Reachable and connected but a field is missing or sentinel — `HFR 0` /
   `Stars -1` on a calibration frame, `Index out of range` before the first
   sub, the 24-hour meridian idle value → **entity `unknown`**, not
   unavailable.

**`log-when-unavailable`** (Silver): log the transition once at `warning`,
recovery once at `info` — never per cycle. `poll_all`'s
`except: results[key] = {}` disappears; that swallow is what produced the
"publishes defaults instead of unavailable" bug.

## 8. Testing

```
tests/
├── unit/                      no HA import — milliseconds
│   ├── test_v2_client.py      envelope discrimination, paths, params
│   ├── test_v2_schema.py      DRIFT GUARD: fixtures vs generated TypedDicts
│   ├── test_v2_mapper.py      wire → models, incl. v2 quirks
│   ├── test_derive.py         image scale, HFR″, tree walk, progress, sentinels
│   ├── test_events.py         event parsing + /event-history fold
│   └── test_blueprints.py     (existing)
├── ha/                        pytest-homeassistant-custom-component
│   ├── test_config_flow.py    100% — Bronze
│   ├── test_init.py           setup/unload, NotReady vs Error, runtime_data
│   ├── test_devices.py        hub + via_device, creation on *-CONNECTED
│   ├── test_entities.py       registry snapshot
│   ├── test_availability.py   the three levels
│   └── test_actions.py        ServiceValidationError vs HomeAssistantError
├── fixtures/                  recorded from the rig
└── snapshots/                 syrupy .ambr
```

**Fixtures are captured, not written.** `scripts/capture_fixtures.py` performs
read-only `GET`s against a live rig and writes `tests/fixtures/<endpoint>.json`,
committed and re-runnable per ninaAPI release. Hand-written fixtures would have
encoded `'Siderial'` from the spec and been wrong.

**The corpus needs states, not a snapshot:**

| State | What it exercises |
|---|---|
| imaging *(captured)* | happy path |
| before the first sub | `Index out of range` → `unknown`, not an error |
| dawn flats | `HFR 0` / `Stars -1` sentinels |
| idle / parked | meridian 24 h sentinel; `flats/status` `-1` iterations |
| sequence complete | the progress-never-reaches-100% bug |

Each converts a past bug into a permanent regression test. Capture them
opportunistically; implementation does not block on them.

**The drift guard is load-bearing.** It replays every fixture against the
generated TypedDicts and fails on any field or enum value the types disallow,
turning a ninaAPI upgrade into a reviewable diff. It would have caught all three
drifts in §3.2.

**Snapshots are how a 200-entity restructure gets reviewed.** `test_entities.py`
and `test_devices.py` snapshot the registries via syrupy; the `.ambr` diff *is*
the rename mapping — every `unique_id`, entity id, category and default-enabled
flag in one artifact. Snapshots sit alongside behavioural tests, not instead of
them.

**Coverage is deliberately uneven:** 100% on `config_flow.py` (Bronze); high on
`derive.py` and `v2/mapper.py` because that is where the bugs live and they are
pure; no global 95% gate.

**CI** runs both suites plus **hassfest** and the **HACS validation action** —
which would have caught `wip/v2.0`'s regressed manifest immediately.

**Tests lead each phase.** The fixture corpus means most tests can be written
from recorded reality before the code exists.

## 9. Phasing

A `v2` integration branch off `main`; each phase a PR into it; `v2` → `main` and
tag `2.0.0` at the end.

**Ordering constraint:** replacing `api.py` breaks all eight platforms at once,
so the new stack is **built alongside the old and switched over per-platform**.
Every PR stays green on its own tests.

| Phase | Content | Size |
|---|---|---|

**Phase 3 carries the risk** — eight platforms, ~155 entities, every id
changing. The registry snapshots make each platform PR reviewable as a diff.

`wip/v2.0` stays as a read-only reference through phases 2–5; delete after
2.0.0 ships.

**On planning granularity.** This spec is deliberately larger than one
implementation plan should be. Phases 0–2 are tightly coupled and plan well
together; **phase 3 warrants its own plan** (eight platforms, ~164 entities,
every id changing); phases 4–6 plan together. Expect three implementation
plans against this one design, not one.
