## 0. Glossary

**Project-local terms.** These are used as proper nouns throughout.

| Term | Meaning |
|---|---|
| the seam | The `api/` package boundary. Nothing above it knows a wire format. §4.1 |
| the envelope | v2's `{Success, Error, StatusCode, Response, Type}` response wrapper. §3.5 |
| the fold | `session.py`'s idempotent set-union of frames keyed on identity. §4.4 |
| the drift guard | The test comparing captured fixtures against generated types. §8.5 |
| first-sight rule | Create an entity/device on first observation, keep it thereafter. §5.2.2 |
| the blanket rule | `"NaN"` → `None` across every numeric field, no allowlist. §4.2 |
| a sentinel | An in-band value meaning "no reading" — `"NaN"`, `HFR 0`, `-1` iterations, 24 h to flip. §7.3 |
| the fast tier | The 10-second poll. §6.1 |
| the floor | The 5-minute backstop poll for event-driven data. §6.1 |
| a vertical slice | One entity migrated end-to-end through every layer, to prove the shape. §9 |

**Domain terms**, for a reader who is not an astrophotographer.

| Term | Meaning |
|---|---|
| N.I.N.A. | Nighttime Imaging 'N' Astronomy — the Windows capture application this integrates with |
| Advanced API | The N.I.N.A. plugin exposing HTTP + WebSocket. Versioned separately from N.I.N.A. |
| ASCOM | The Windows driver standard for astronomy hardware. `ObservingConditions`, `CoverCalibrator` etc. are its device interfaces |
| sub | A single light exposure. A night is tens to hundreds |
| light / flat / dark / bias | Frame types. Only lights are of the sky; the rest are calibration |
| HFR | Half-Flux Radius — star size in pixels; the standard focus-quality metric |
| ADU | Analog-to-digital unit — raw pixel value. Flats are bright (~33,000), lights dim (~550) |
| plate solve | Determining where the telescope is actually pointing from the star field |
| meridian flip | A German-equatorial mount must rotate 180° when the target crosses the meridian |
| J2000 / JNOW | Coordinate epochs. J2000 is fixed; JNOW is today's, differing by precession (~0.36° now) |
| dither | Shifting slightly between subs so sensor defects average out |
| Target Scheduler | A N.I.N.A. plugin that chooses targets autonomously. Emits `TS-*` events |
| SQM / sky quality | Sky brightness in mag/arcsec² — a light-pollution measure |

## 1. Purpose, scope, non-goals

Bring the integration into line with the Advanced API as it exists today, and
with Home Assistant's conventions. Three drivers:

- Endpoint paths, parameters and response fields drifted from the API; several
  entities and services have never worked.
- Every entity hangs off one device, so two rigs cannot coexist, and driver
  metadata sits in entity attributes where Home Assistant does not expect it.
- Polling is far more expensive than necessary, and the WebSocket is used only
  as a hint to re-poll rather than as a data source.

Ships as a single `2.0.0`.

### 1.1 Non-goals

No migration machinery. No multi-rig support before phase D. No ninaAPI v3. No
authentication. No `diagnostics`, `repairs` or `discovery`. No dome validation
(§5.3.1). No Silver or Gold quality-scale conformance beyond what falls out
naturally.

### 1.2 Abort criterion

Phase C is XL and this integration drives a live observatory. If it stalls,
`v2` is parked and 1.4.x continues to ship; nothing in phases A–B is
user-visible.

## 3. Verified findings

All measurements are from a rig running **Advanced API 2.2.15.2 / N.I.N.A.
3.2.0.9001**, 2026-09-03/04, over Tailscale. Re-measure with
`scripts/measure_payloads.sh` (phase A) so later comparisons are like-for-like.

### 3.1 Dead endpoints — fixed in 1.4.5

Nine paths in `api.py` did not exist. Seven are fixed on
`fix/api-endpoint-paths` (10 commits, 101 tests), including one that mattered
far more than a dead path: `/equipment/mount/slew` reads RA in **degrees** while
the service takes decimal **hours**. Fixing only the path would have sent the
mount eight hours away, silently — 22.07 is a valid RA read either way.

Carried into 2.0:

| Item | Why |
|---|---|
| `/image/latest` → `/image/{index}` or `/prepared-image` | response-shape change |
| `/sequence` → `/sequence/json` | different shape entirely (§3.3) |
| 53 dead `ENDPOINT_*` constants | paths move into `api/v2/client.py` |
| `camera_capture` ignores exposure time | sends `time`, API reads `duration`; `binning`/`filter_index` bind nothing — service redesign |
| `sequence_load` never loads the sequence | sends `path`, API reads `sequenceName` — service redesign |

### 3.2 The spec is unreliable for types **and for request parameter names**

Names mostly match — nine of eleven device schemas field-for-field, with
`CameraInfo` missing `HasBattery` and `MountInfo` missing `CanSlewAltAz`.
`FlatDeviceInfo` validated 17/17 against connected hardware. `DomeInfo` cannot
be validated (§5.3.1).

**Response types are wrong**:

| Field | Spec | Wire |
|---|---|---|
| `WeatherInfo.CloudCover`, `DomeInfo.Azimuth` | `integer` | `"NaN"` |
| `WeatherInfo.Humidity`, `Pressure` | `integer` | 59.3, 958.5 |
| `WeatherInfo.RainRate`, `SkyBrightness`, `SkyTemperature`, `WindGust` | `string` | numeric |
| `RotatorInfo.Position`, `MechanicalPosition` | `integer` | **335.0736**, 53.86 |
| `MountInfo.TrackingRate` | `object` | `{}` |
| `CameraInfo.Gains` | `array` | `[]` |
| `/livestack/status` `Response` | `object` with a `Status` field | the bare string `"Running"` |
| `MountInfo.TrackingMode` | `Literal[…'Siderial'…]` | `'Sidereal'`, and absent — not `null` — when disconnected, along with 13 other keys (`Coordinates`, `DeviceId`, `Name`, `DisplayName`, `TrackingModes`, `PrimaryAxisRates`, `SecondaryAxisRates`, `SupportedActions`, five `*String` fields): the connected Mount carries 51 keys, the disconnected 37 |

**Request parameter names are also wrong, and a wrong name is a silent no-op.**
The spec declares `/equipment/flatdevice/set-light`'s parameter as literally
`True`. Measured:

| Call | Result |
|---|---|
| `set-light?True=true` | `Success: true` — **panel unchanged** |
| `set-light?on=true` | `Success: true` — panel on |

Parameters are read manually and default silently: `set-brightness` with **no
parameter at all** answered `Success: true`.

**Requirement.** Never generate request parameters from the spec. The drift
guard (§8.5) covers response shapes only; request parameters are verified by
live probe and pinned by test.

### 3.3 Poll cost, and payload growth

```
/sequence/state             57,234 B   ← 47,879 B earlier the same evening
/profile/show?active=true   14,396 B
/equipment/info              7,245 B
/sequence/json               8,418 B   ← 6.8× smaller, and recommended by the spec
image-history (both calls)      669 B
```

> *Rationale.* `/sequence/state` embeds `SchedulerProgress.ProgressItemList`, an
> append-only row per Target Scheduler step — 51 rows by 23:30, +16% in one
> evening. `/sequence/json` uses a hand-written per-type map; the spec says of
> it: *"generally advised to use over state since it gives more reliable
> results."*

Growth is process-scoped, measured across one N.I.N.A. lifetime and the restart
that ended it:

| | mid-session (12 frames) | dawn (122) | after restart (0) |
|---|---|---|---|
| `/image-history?all=true` | 5.4 KB | **62.3 KB** | 71 B |
| `/sequence/state` | 47.9 KB | 57.2 KB | 22.0 KB |
| `/event-history` | 27.7 KB / 233 ev | 65.5 KB / **628 ev** | 1.1 KB / 13 ev |
| `/image-history?count=true` | 71 B | 72 B | 70 B |

`/equipment/info` saves only ~7% of bytes over 11 separate `/info` calls; its
value is **11 round-trips → 1** and an **atomic snapshot**.

Re-measured like-for-like on 2026-09-05 against the same rig, mid-session with
27 frames down: `/equipment/info` 7,236 B, `/sequence/json` 8,418 B,
`/image-history?count=true` 71 B, `/application-start` 104 B, `/version` 79 B,
bare `/image-history` 591 B, `?all=true` 14,268 B, `/event-history` 28,373 B,
`/sequence/state` 53,792 B, `/flats/status` 135 B, `/livestack/status` 78 B,
`/equipment/focuser/last-af` 1,872 B. Every figure this section names is within
1%, so the tiering arithmetic below stands unchanged.

### 3.4 Event coverage

68 events documented. A full night emitted **628 events across 44 distinct
types, none undocumented**. Independent cross-check: `IMAGE-SAVE` fired exactly
122 times against 122 frames in `/image-history` — the two paths see the same
frames, which is §4.4's premise.

Five things cannot carry a tier on their own:

| Endpoint | Event-driven? | Evidence |
|---|---|---|
| `/sequence/json` | **No** | Over a full night: `SEQUENCE-STARTING` **0**, `SEQUENCE-FINISHED` **1** (at 07:06, session end). Per-instruction `Status` is a bare `RaisePropertyChanged` for WPF binding — nothing subscribable. `SEQUENCE-STARTING` also fires *after* the tree resets to `CREATED`, and `SEQUENCE-FINISHED` carries no payload. So nothing bounds a session *start*. |
| `SEQUENCE-ENTITY-FAILED` | **Unavailable** | Emitted only by a "Send Error to WebSocket" trigger the user places manually. Not in this sequence. |
| `/profile/show` | **Switches only** | `ProfileService.ProfileChanged` has one call site — `SelectProfile`. Editing settings emits nothing. |
| `/equipment/focuser/last-af` | **Success only** | `BroadcastSuccessfulAutoFocusRun` has one call site. A failed AF gives `AUTOFOCUS-STARTING` then silence. The report file is written **per attempt, before the verdict**, and the endpoint returns the newest — so a rejected run overwrites "last AF" with no success flag. |
| `/flats/status` | **No event exists** | `FLAT-*` events are flat-*panel hardware*, not capture progress. |

Reliable, with a full night's counts: `*-CONNECTED`/`*-DISCONNECTED` for all
eleven devices (1 each), `IMAGE-SAVE` (122), `MOUNT-HOMED` (80),
`GUIDER-START`/`-STOP` (79/24), `AUTOFOCUS-POINT-ADDED` (65), `TS-TARGETSTART`
(56), `STACK-UPDATED` (55), `FILTERWHEEL-CHANGED` (49), `GUIDER-DITHER` (20),
`ROTATOR-MOVED` (10), `SAFETY-CHANGED` (2), `STACK-STATUS` (2),
`MOUNT-BEFORE-FLIP`/`-AFTER-FLIP` (1 each), `FLAT-COVER-*`, `ERROR-PLATESOLVE`
(1).

Two of those validate design decisions directly:

- **`AUTOFOCUS-STARTING` 8 against `AUTOFOCUS-FINISHED` 7** — one unmatched
  start, which is exactly the failure §4.4 detects, and it occurred on an
  ordinary night.
- **`MOUNT-BEFORE-FLIP` fired**, so §11's phase-D trigger is proven, not assumed.

**`IMAGE-SAVE` has two shapes.** The live socket carries `ImageStatistics` and
no `Time`; `/event-history` carries `Time` and **no statistics** — all 28 stored
copies are exactly `{Event, Time}`.

**Confirmed by live capture.** A 1 s dark produced an `IMAGE-SAVE` whose
`ImageStatistics` and the matching `/image-history` record are **field-for-field
identical**, including `Date` (`2026-09-04T13:49:05.4202709-05:00`, offset-aware
local) and `Filename`. §4.4's identity key holds on both paths with no fallback
needed.

**`Index` does not exist on either path**, though the AsyncAPI spec documents it
on `ImageStatistics`. Another spec drift.

**Calibration sentinels are frame-type-specific.** All 67 flats in one session
reported `HFR 0` **and** `Stars -1`; the test dark reported `HFR 0` and
**`Stars 1`**. Calibration is therefore keyed on `ImageType` — the explicit set
`FLAT`, `DARK`, `BIAS`, `DARKFLAT` — not on either sentinel: a clouded light
reports `HFR 0` too, and `Stars == -1` is not universal. `HFR 0` is a secondary
null-out inside lights; `LIGHT`, `SNAPSHOT` and an absent type keep their
readings. `RmsText` (`'Tot: 0.26 (0.42")'`) carries guide-camera pixels first
and arcseconds in brackets; the arcsecond figure is the one comparable across
rigs, and `0.00` on a light is no guiding, not perfect guiding.

**An API-initiated capture sets `TargetName` to `"Snapshot"`.** Harmless for a
dark, but a `light` captured through the API would corrupt any target sensor
derived from the last light frame.

**Three timestamp formats**, two naive and indistinguishable by shape:

| Class | Example | Semantics |
|---|---|---|
| mediator (211) | `2026-09-03T23:26:19.36-05:00` | offset-aware local |
| `TS-*` (32) | `2026-09-04T02:15:32.78` | naive **UTC** |
| log-scraped (1) | `2026-09-03T21:54:26.93` | naive **local** |

The timezone assumption is keyed on the **event name** — a table in
`api/v2/mapper.py`.

`ERROR-*` events are log-file regex scraping: `ERROR-PLATESOLVE` matches ASTAP
only; `ERROR-AF` appears dead. `{DEVICE}-INFO-UPDATED` is dead code —
`SendConsumerEvent` returns unconditionally. `TS-*` payloads carry
`"Coordinates": {"RA": [], …}` — empty arrays where scalars belong — and the
"Send WebSocket Event" instruction puts a **bare string** in `Response`.

### 3.5 Failure shapes — the HTTP status is a lie

`CoreUtility.WriteToResponse` never assigns `context.Response.StatusCode`. So
every *handler-level* outcome is HTTP 200 with the real code in the body:

| Case | HTTP | Body |
|---|---|---|
| unknown path | 404 | EmbedIO HTML — pre-handler |
| malformed param | 400 | EmbedIO HTML — pre-handler |
| `Index out of range` | **200** | `{Success:false, StatusCode:400}` |
| `"Sequence is not initialized"` | **200** | `{Success:false, StatusCode:409}` |
| sequence serialization failure | **200** | **empty body, no envelope** |

**Commands are asynchronous, and `Success: true` does not mean the state
changed.** Measured: `set-light?on=true` returned success while an immediate
re-read still showed `LightOn: false`; it changed seconds later. Combined with
§3.2's silent parameter defaulting and §5.3.4's silent clamping: **no command on
this API can be confirmed from its own response.**

**`"NaN"` is the most common sentinel.** .NET serializes `double.NaN` as a JSON
**string**. Five fields with nine devices connected; **nineteen** with weather,
mount, focuser and dome disconnected, including every `WeatherData` channel.
It is also overloaded — disconnected, momentarily unreadable, *and* not
implemented by this driver — with nothing to tell them apart.

**`Success: false` on success is enumerable.** Seven handlers assign it from a
driver boolean, answering `Success: false, Error: "", StatusCode: 200`:
`guider/clear-calibration`, `dome/set-follow`, `mount/tracking`, the three
`waitForResult` branches of `mount/slew`, `framing/determine-rotation`.

**No authentication exists** — `reauthentication-flow` is exempt.

### 3.6 A N.I.N.A. restart wipes the history the design replays

Observed: `/application-start` moved to `2026-09-04T10:58:59` and in the same
instant `/event-history` fell 244 → 13 and `/image-history` 122 → 0. Both are
in-process state.

An empty history answers three ways: bare `/image-history` →
`Index out of range`; `?all=true` → `{"Response": []}`; `?count=true` → `0`.
Only the first looks like a failure.

**Three independent restart signals**, all observed across two restarts in one
day:

| Signal | Behaviour |
|---|---|
| `/application-start` | changes (`10:58:59` → `13:54:50.907`) |
| `/image-history?count=true` | **decreases** — a monotonic counter going backwards |
| `/event-history` | resets, and can be **completely empty** |

`/application-start` is authoritative; the count decrease is a free
corroboration on the same tier. An empty `/event-history` at setup is a normal
state, not a failure.

**There is a ~7.5-second window at N.I.N.A. startup during which the sequencer
is not initialized.** Measured: the API answered at 0.3 s with
`{"Error": "Sequence is not initialized", "StatusCode": 409}` and returned a
tree at 7.8 s. Home Assistant will land inside it whenever the two restart
together — after a power cut, for instance — so §7.1's handling of that response
is on the ordinary startup path, not an edge case.

**Requirement.** Every folded frame and event is tagged with the
`/application-start` value in force when it was received, and the process
boundary is **derived by filtering on that generation** — never by clearing the
set. §4.4.

> *Rationale.* Clearing races a concurrent poll, produces a false positive on
> the first read when no baseline exists, and loses events that arrive during
> the refetch. Filtering is the same idiom §4.4 already uses for the session
> boundary, so one concept covers both.

### 3.7 Slew epoch — resolved

All three branches of `/equipment/mount/slew` construct
`new Coordinates(Angle.ByDegree(ra), Angle.ByDegree(dec), Epoch.J2000)`;
`/equipment/mount/sync` and `/sequence/set-target` are identical. N.I.N.A.
transforms to the mount's own `EquatorialSystem` internally.

**Requirement.** Send J2000 in degrees. **Never pre-transform.**

**And the round trip is asymmetric.** `MountInfo.Coordinates` /
`RightAscension` are reported in the *mount's* epoch (JNOW here) and in
**hours**. Feeding a reported RA back into `/slew` is wrong twice — a 15× unit
error and a precession error. The payload carries an explicit `Epoch` field for
this reason.

### 4.1 The seam

`errors.py`, `models.py` and the package root are version-independent.
*Everything* that knows a wire format lives under `api/<version>/`. Above
`api/`, the client TYPE (`NinaClientV2`) may be imported; wire data and wire
vocabulary may not — nothing above `api/` imports `api.v2.mapper` or
`api.v2.schema`, and no dict crosses the boundary.

### 4.2 Type layers

1. **`v2/schema.py`** — generated `TypedDict`s from the committed spec, via
   `scripts/generate_schema.sh` with a pinned `datamodel-codegen`. Never
   hand-edited.
2. **`v2/client.py`** fetches, unwraps, returns those TypedDicts.
3. **`api/models.py`** — hand-written frozen dataclasses, sized by what entities
   consume, built by `v2/mapper.py`.

`manifest.json` keeps `requirements: []`; the generator is dev-only.

**Models distinguish "never seen" from "present but disconnected"** —
`camera: CameraModel | None` plus `CameraModel.connected: bool`. §5.2.2 and
§7.3 both need this from one snapshot.

**`models.py` is closed to fields no entity, service, `session.py` or
`derive.py` consumes.** A guideline, not a test — the enforcement needs an
exemption list on its first service-only field.

**The mapper owns all wire quirks:** the blanket `"NaN"` → `None` rule over
every numeric field; calibration keyed on `ImageType` with `HFR 0`, `Stars -1`
and a zero guide RMS as secondary null-outs (§3.4); **a `Connected: false`
block mapping with every reading `None`** — only `connected`, `meta` and the
capability flags survive, because a disconnected driver's `Position 0`,
`StepSize 0` and `ShutterNone` are template defaults, not readings; `Guider
PixelScale 0` and `Camera Battery -1` as non-readings; the meridian sentinel
(§11); the three timestamp classes keyed by event name; `'Sidereal'`; `UTCDate`
having no offset; per-mount `TrackingModes`; `TS-*` empty-array coordinates; a
bare-string `Response`. If a sentinel reaches `derive.py`, `models.py` carries
sentinel values and the seam is broken.

**`derive.py` gets only version-independent maths:** image scale, HFR→arcsec,
progress arithmetic, session-boundary computation. The `/sequence/json` walk is
not pure — the tree shape is partly a Target Scheduler fact — so the mapper
normalizes it into a `SequenceNode` model that `derive.py` walks.

### 4.3 Coordinator ownership

One `DataUpdateCoordinator[NinaData]`. `NinaData` is a frozen dataclass holding
the normalized snapshot, `SessionStats`, and `AutoFocusState`.

**The coordinator owns the accumulated frame and event set.** `session.py` is
stateless and receives it as an argument.

**All mutation happens on the event loop**, and `NinaData` is assembled from the
live set at the moment of publication with no `await` between reading the set
and freezing the dataclass.

> *Rationale.* Four writers touch the set — the poll, the WebSocket callback,
> `/event-history` replay, and the restart reseed. Without this, a poll that
> awaits `/equipment/info` while `IMAGE-SAVE` arrives publishes a snapshot
> assembled from a pre-event read, and the frame appears, vanishes, reappears.

### 4.4 `session.py` — a pure fold

`fold(frames, events, generation) -> SessionStats`.

**Frame identity is `(Date, Filename)`**, confirmed present and identical on
both the push and poll paths (§3.4). Push, poll and replay become the same
idempotent operation; arrival order stops mattering.

**`Date` is the save time, not the exposure start** — start + exposure +
download. Verified against FITS headers from the same session: `DATE-LOC`
`21:39:10.786` with a 300 s exposure appears in the API as
`21:44:18.907-05:00`, and `02:35:12.890` with 600 s appears as
`02:45:17.938-05:00`. Both paths take it from the API, so identity stays
consistent; but anything reasoning about *when a frame was taken* must subtract
`ExposureTime`.

**Aggregates are computed once from a deterministic (sorted) iteration**, never
accumulated incrementally.

> *Rationale.* Order-independence over floats is false under incremental
> accumulation — summing HFRs in different orders differs in the last bits, and
> frozen-dataclass equality is exact.

**The session boundary is the most recent local noon** (rollover hour
configurable — the `rollover_hour` option, §4.6), computed from frame `Date` in
`derive.py`. *Local* is the **rig's** local: frame dates carry the rig's UTC
offset, so the coordinator measures the boundary against a clock in that offset
(the client caches it from the mount's `Coordinates.DateTime` on every
`/equipment/info`) and falls back to Home Assistant's zone only until the mount
has been read. Measured in UTC, 12:00 is 07:00 on a UTC−5 rig — inside its
dawn flats. Expose `sensor.session_start`.

> *Rationale.* This is what an astrophotographer means by a session, and what
> N.I.N.A.'s own image-history dockable and Target Scheduler mean. It needs no
> events — the earlier `SEQUENCE-STARTING` basis was unusable (§3.4) — and it is
> correct both when N.I.N.A. restarts mid-day and when it runs for days across
> several nights. Process lifetime would have reported night 1 + 2 + 3.
>
> Validated against a real midnight-spanning session: frames at local
> `2026-09-03T21:39` and `2026-09-04T02:35` both resolve to session start
> `2026-09-03T12:00`. A midnight rollover would have split one night in two.

Because `Date` is the save time, an exposure begun just before the rollover
lands in the following session. At a noon rollover this cannot occur in
practice.

**A session spans targets, filters and exposure lengths.** One observed night:

```
targets   : Dark Shark Nebula, Lobster & Bubble, NGC 281, Wizard Nebula
filters   : B, L, O, R, S
exposures : 180, 300, 600 s
```

Two consequences:

- **Integration time sums actual `ExposureTime`**, never count × nominal. On
  that night the correct total is **6.20 h**; count × shortest-exposure gives
  2.75 h — a 2.25× error.
- **Session-wide aggregates are dominated by whichever target got the most
  frames** — per-target HFR means ranged 1.429 to 1.667 against a session-wide
  1.513. The scalar aggregates stay as they are, but the per-target and
  per-filter breakdown goes in the summary sensor's attributes rather than
  becoming new entities.

**The process boundary is the generation tag** (§3.6), applied by filtering.

**Autofocus failure is folded, not correlated.** An `AUTOFOCUS-STARTING` with no
matching `AUTOFOCUS-FINISHED` within `FocuserSettings.AutoFocusTimeoutSeconds`
is a failure; it drives `binary_sensor.autofocus_failed` and feeds
`event.nina_error`. State is derived from the folded set on read, so there is no
timer to leak. **An interrupted run is aborted, not failed:** `SAFETY-CHANGED`
with `IsSafe: false`, `SEQUENCE-FINISHED`, `MOUNT-PARKED`, any `*-DISCONNECTED`
or a later `IMAGE-SAVE` landing inside the timeout window cancels the run
(`running_since None, failed False`) — the dawn corpus's one unanswered start
was followed 37 s later by the safety monitor tripping. An interruption after
the window closed clears `running_since` but the verdict stands. A `FINISHED`
is the report, not a verdict (`AutoFocusState.last_finished_at`); phase C reads
success from `/equipment/focuser/last-af` — R² against `RSquaredThreshold`.

### 4.5 No `Operation` protocol

Long-running commands are fire-and-forget: `slew`, `capture`, `auto_focus`,
`cool_camera` and `park` return when the API accepts them.

> *Rationale.* Under v2 there is no request id — that is exactly what v3's
> `ProcessId` adds — so a completion event cannot be attributed to a caller.
> Autofocus on this rig is overwhelmingly *sequencer*-initiated, so the run
> being watched usually has no Home Assistant caller at all, and a
> sequence-triggered completion would resolve a handle it has nothing to do
> with. Only three of the five commands have completion events, so the other two
> would report success while still running. The genuine need behind the idea —
> AF-failure detection — is a fold over the event stream (§4.4), which is
> correct for sequencer-initiated runs and needs no protocol.
>
> When v3 ships, adding a handle type to five signatures is a bounded mechanical
> change. The seam that does the real work — `models.py`, `mapper.py`, the
> `v2/` package — is unaffected.

Event subscription is `subscribe(callback)`. No topic parameter until there are
channels to map it to.

### 4.6 Config entry and options

| Key | Where | Default | Range |
|---|---|---|---|
| `host` | data | — | required |
| `port` | data | `1888` | — |
| `instance_name` | data | `"N.I.N.A."` | — |
| `poll_interval` | data, overridable in options | `10` | 5–60 s |
| `rollover_hour` | options | `12` | 0–23 |

`unique_id` is `f"{host}:{port}"`: the API exposes no stable installation
identity, and the address is the one thing two instances must differ in. The
host is **normalised** (`strip().lower()`) before the unique id is built and
stored in that form — hostnames are case-insensitive, so `NINA.local` and
`nina.local` are one rig — and the unique id is set and the duplicate aborted
**before** the probe, so adding a configured rig again costs no HTTP call.

`instance_name` is the entry title and the prefix on every device name (§5.1).
**Entries created before 2.0 carry no `instance_name`**, so setup falls back to
the entry title — which is what those entries have, and what the flow now writes
into both. A name another entry already answers to is **refused**
(`name_in_use` on the `instance_name` field, compared against each entry's own
`instance_name` or, for a pre-2.0 entry, its title): two rigs sharing one would
name their devices identically and the second set would collide into `_2`
entity ids. Blank names are refused by the schema — `vol.Strip` before the
length check, since a length check alone accepts `"   "`.

`rollover_hour` is in the RIG's local hours, for the same reason the fold is
(§4.4): a rig whose Windows clock runs UTC — common on hosted setups — reports
every timestamp in that clock, so a noon default lands at 07:00 site time for a
UTC−05:00 site, inside the dawn flat run, splitting one night in two.

The connection is probed with `NinaClientV2.get_versions()` (Bronze
`test-before-configure`), and the flow's error mapping mirrors setup's:
`NinaConnectionError`/`NinaUnavailableError`/`NinaCommandError` →
`cannot_connect`, `NinaEndpointError`/`NinaRequestError` → `unsupported_api`,
anything else → `unknown`.

## 5. Entity and device model

### 5.1 Device model

Hub service device, one child per equipment type linked by `via_device_id`,
driver metadata synced into the registry. `DriverVersion` is the `sw_version`.

Identifiers are `(DOMAIN, entry_id)` for the hub and `(DOMAIN, f"{entry_id}_{kind}")`
for a child, `kind` being the `EquipmentSnapshot` slot name. A child is named
`f"{instance_name} {label}"` — "Flat Panel", "Filter Wheel", "Safety Monitor",
"Switch", "Weather" — which under `has-entity-name` is what entity ids derive
from.

`device.async_sync_devices` is the **only** writer of device metadata. It runs
on every coordinator publish and creates a child for each snapshot slot that is
not `None` — the coordinator's latched first sight — so a device that connects
hours after Home Assistant started still appears, and a swapped driver replaces
the `Name` and `DriverVersion` on record. A field the driver is not reporting is
omitted rather than written as `None`: a disconnected device drops its whole
identity, and writing that through would blank the registry. Entities claim the
identifiers and nothing else, because metadata frozen into an entity's
`device_info` at construction would never be filled in.

A device is never removed by a poll — equipment is routinely down, and one that
came and went would take its entity ids with it.
`async_remove_config_entry_device` is the way out (Gold `stale-devices`): it
accepts a child whose slot is `None` in the current snapshot, and one carrying
an identifier scheme no longer written; it refuses the hub and anything the rig
still reports.

The hub carries `configuration_url` — `http://{host}:{port}`, the entry's own
address, which is the only page the Advanced API serves.

`DriverInfo` is not mapped — the rotator and flat panel both return the ASCOM
template default (`"Information about the driver itself. Version: …"`), though
the filter wheel returns real firmware. Not universally useless, just unreliable.

### 5.2 Cuts

`wip/v2.0` defines ~203 entities.

#### 5.2.1 `*_connected` becomes availability (−10)

Silver `entity-unavailable`. Ten devices lose theirs; `unavailable` is
observable in automations.

**The safety monitor is the exception.** Keep
`binary_sensor.safety_monitor_connected` as `DIAGNOSTIC`, and safety/weather
blueprints trigger on `to: ['off', 'unavailable', 'unknown']` (phase D).

> *Rationale.* A disconnected safety monitor would make `safety_is_safe`
> unavailable, so a roof-close automation on `to: "off"` does not fire.
> `to: "unavailable"` cannot substitute — it conflates device-disconnected,
> N.I.N.A.-unreachable, HA-restarting and coordinator-failed. This is the only
> asymmetric-risk entity in the set.

#### 5.2.2 Dynamic creation, at two granularities (Dome −17, FlatDevice −6, conditional)

**One rule, one shared helper, two granularities:**

- **Devices** — create on first observation of the equipment, keep thereafter.
  Gold `dynamic-devices`. Persistence comes from the device registry.
- **Weather channels** — create on first non-`NaN` reading, keep thereafter.
  Persistence comes from the **entity registry**: at setup, enumerate this
  entry's existing weather entities and add them immediately, then add new ones
  as they appear.

**What "observed" means.** `/equipment/info` always emits all eleven device
blocks (a full `Dome` block on a rig that has never had one), so block presence
proves nothing. A device is *observed* once it has carried a `DeviceId`;
disconnection removes it, so the coordinator latches the observation for its
lifetime. The mapper stays stateless — a disconnected device maps to
`connected=False` with no `DeviceId` — and the coordinator blanks every
never-observed slot to `None` before publishing.

> *Rationale for registry-as-truth.* `async_setup_entry` runs before any data
> arrives. Without recovery from the registry, every weather entity disappears
> on every HA restart and reappears minutes later — breaking automations and
> fragmenting recorder history.

**When the active weather source differs from the one that established a
channel, that channel is `unavailable`, not `unknown`.** Track the
`WeatherData.DeviceId` that last produced a non-`NaN` reading per channel.
`unique_id` stays source-independent.

> *Rationale.* Two sources on this rig are disjoint in both directions — the
> physical station provides `SkyBrightness`/`SkyTemperature` but not
> `CloudCover`; OpenMeteo the reverse. Keying `unique_id` on `DeviceId` would
> change entity ids on a source swap, breaking automations permanently to avoid
> a rare event. Accumulating the union leaves channels at `unknown` forever,
> which is a lie — the source *cannot* report them. `unavailable` is the honest
> state and composes with §5.2.1's trigger set.

Add `sensor.weather_source` so the active source is inspectable.

**The rule applies only where absence is a permanent driver property** — weather
channels. Not `CameraInfo.CoolerPower` or `MountInfo.TimeToMeridianFlip`, which
are transiently `NaN`; a rig whose camera is warm at setup must not lose its
cooler-power entity.

Pair devices with `async_remove_config_entry_device` so a sold dome can be
deleted.

**Cold start:** configuring in daylight yields no weather entities until dusk.
Documented in README.

| `sensor.dome_azimuth` | `number.dome_azimuth` |

- **`sensor.focuser_position` reinstated**, disabled by default, with

### 5.3 Subsystem specifics

#### 5.3.1 Dome — shipped untested

There is no dome available and no prospect of one, so `DomeInfo` cannot be
validated, and it is the one subsystem where the spec is known wrong (five
missing fields, `Azimuth` typed `integer` while sending `"NaN"`).

**Requirement.** Dome entities ship. Their descriptors carry `verified: False`
in code, enforced by a test asserting every dome descriptor has the marker.
Their logic stays conservative — no derived state, no sentinel interpretation
beyond the blanket rule. README states plainly that dome support is
spec-derived and untested against hardware, and invites a dome owner to report
findings. The drift guard cannot see them (§8.5); a synthetic
`tests/synthetic/dome_connected.json` derived from a real *disconnected* capture
exercises the mapper path and asserts branch reachability only, never values.

#### 5.3.2 Livestack

**`switch.livestack` is retained** — state from `/livestack/status`, `turn_on`
→ `/livestack/start`, `turn_off` → `/livestack/stop`. Its state *is* the status,
so `binary_sensor.livestack_running` and `sensor.livestack_status` stay cut
under §5.2.3's mirror rule; nothing is lost.

> *Rationale.* Livestack can be started and stopped at any time, and the event
> stream cannot express that. `STACK-UPDATED` says a stack advanced; its absence
> is indistinguishable from "running but no new frame yet". Only
> `/livestack/status` reports on/off. Observed overnight: 55 `STACK-UPDATED`
> against **2 `STACK-STATUS`** — the latter is the start/stop transition signal.

**Freshness:** refetch `/livestack/status` on `STACK-STATUS`, with the floor
tier as backstop. The event carries a `Status` (`"Running"`, `"Stopped"`)
alongside `{Event, Time}`, but it reports the transition the plugin announced
rather than the server's own state — only `/livestack/status` does that — so the
status is read back rather than taken from the push.

The endpoint is safe to poll unconditionally: per the spec it "cannot fail, even
if the livestack plugin is not installed… status is tracked by the server". A
rig without the plugin therefore sees a switch that reads stopped and does
nothing — acceptable, and cheaper than gating creation on plugin detection.

**Compare the status string case-insensitively.** The OpenAPI enum is
`[running, stopped]`; a live rig was recorded returning `"Stopped"`.

**Add `image.livestack`** from `/livestack/image/{target}/{filter}`, with
`/livestack/image/available` supplying the target/filter pairs — the
accumulating stack is a better dashboard image than the last raw sub.

`/livestack/start` and `/stop` "cannot fail" either, so neither confirms
anything (§3.5). The switch reads its state back from `/livestack/status`, never
from the command response.

#### 5.3.3 Flats — disabled by default

`/flats/status` observes only flats started through the API. This rig runs Target
Scheduler Flats, so it reads `{State:"Finished", TotalIterations:-1,
CompletedIterations:-1}` straight through a completed dawn run — confirmed.
Entities ship `DIAGNOSTIC` and disabled; `/flats/status` sits on the **floor**
tier unconditionally (300 B / 5 min is noise, and a conditional tier would need
cross-layer "someone invoked flats" state).

#### 5.3.4 Flat panel light — three fixes

`light.py`'s docstring asserts a 0–255 brightness range. The range is
per-device: this panel reports `MaxBrightness: 4096`; the owner's previous one
was 256; Alnitak Flat-Man and Flip-Flat report 255, which is why the assumption
survived.

1. **Scale between the driver's `MinBrightness` and `MaxBrightness`.** HA
   brightness 1–255 → `Min..Max`. Measured: HA 255 currently yields **6.2%** of
   output, and the `brightness` property returns the raw driver value, handing HA
   `4096` into a property defined as 0–255. **Guard `MaxBrightness <= 0`** — a
   disconnected panel reports `Min: 0, Max: 0`, which is the ordinary startup
   state.
2. **Validate client-side.** `set-brightness?brightness=99999` **silently clamps
   and answers `Success: true`**. Out-of-range raises `ServiceValidationError`.
3. **`turn_on` sends brightness explicitly.** A bare `set-light?on=true` jumps
   to `MaxBrightness` — measured 0 → 4096. A light that turns on at full output
   is a hazard in a shared observatory.

**Brightness 0 is not off.** `turn_off` calls `set-light`, never
`set-brightness=0`. Gate the `light` on `SupportsOnOff` and the cover on
`SupportsOpenClose`.

**Do not verify by immediate readback** (§3.5). `FLAT-LIGHT-TOGGLED` carries an
empty payload, and `FLAT-BRIGHTNESS-CHANGED` fires repeatedly through a ramp
with inconsistent `Previous` values. Treat both as change hints and re-read.

Also: `light.…flat_panel_light` and `switch.…flat_panel_light` both exist today
for one device. The `light` survives.

#### 5.3.5 N.I.N.A. switch device — enabled by default

- A channel where `Max − Min == StepSize` is **binary** → `switch` platform.
- Read **`Value`**, not `TargetValue`.

On this rig the switch device is an HA→N.I.N.A. bridge exposing two Kasa
outlets, so the entities duplicate ones that exist natively. Accepted — the same
entity through two integrations is ordinary — and the normal case is a real
ASCOM switch (a Pegasus Powerbox and its outlets, dew heaters and
voltage/current channels), which the default should serve.

## 6. Data flow

### 6.1 Tiers

| Tier | When | Calls | Bytes |
|---|---|---|---|
| Fast | 10 s | `/equipment/info` 7,245 B, `/image-history?count=true` 71 B, `/application-start` 104 B | 7,420 B |
| Sequence | 30 s while imaging (§6.2), else 5 min | `/sequence/json` | 8.4 KB |
| Event-driven | on `PROFILE-*` and **`STACK-STATUS`**, queued for the next tick; on **`SAFETY-CHANGED`** and **`*-CONNECTED` / `*-DISCONNECTED`**, refetched immediately (§6.4). `IMAGE-SAVE` queues nothing — its payload *is* the frame, so it feeds the push path and the imaging heuristic; `AUTOFOCUS-FINISHED` queues `/last-af` once that endpoint has a model | `/profile/show`, **`/livestack/status`**, `/last-af`, and **`/equipment/info`** for the immediate two | 0 at rest |
| Floor | 5 min | the event-driven set, `/flats/status` | amortised |
| One-shot | setup, detected restart, socket reconnect | **`/image-history?all=true`** | 62 KB worst case |
| Setup only | — | `/version`, `/version/nina` | — |

```
fast       7,420 B @ 10 s  =  44,520 B/min
sequence   8,418 B @ 30 s  =  16,836 B/min
                              ──────────
                              61,356 B/min ≈ 3.7 MB/h ≈ 37 MB / 10 h night
current                       82,606 B × 6/min ≈ 297 MB / night   → ~8×
```

**`/image-history?all=true` is the only reseed source.** Bare `/image-history`
returns the newest frame only (598 B), so seeding the fold from it would leave
`Session Image Count` reading 1 for the rest of the night.

**`/application-start` is on the fast tier**, at 104 B. It is the restart
detector, and `/image-history?count=true` decreasing is a free corroborating
signal at the same resolution. `?count=true`'s job is the invariant check: fold
size ≠ count ⇒ refetch `?all=true`; count decreased ⇒ new generation.

**Six tiers, one coordinator.** A single `DataUpdateCoordinator` ticking at 10 s
with per-tier due-time checks inside `_async_update_data`. Not three
coordinators.

**Do not refetch on `TS-TARGETSTART`** — it fires once per exposure (27 in 3.8 h)
and its payload already carries `TargetName`, `ProjectName`, `Rotation` and
`TargetEndTime`. Debounce any sequence refetch to ≤1 per 30 s; the sequence
tier owns that budget.

### 6.2 Imaging-in-progress detection

**Requirement.** Infer imaging from activity, not from `/sequence/json` node
status: recent `IMAGE-SAVE`, camera `CameraState`, or a rising
`/image-history?count=true` — all already on the fast tier. Tree status drives
only the *displayed* per-instruction state.

> *Rationale.* Node `Status` persists from the loaded sequence file and from
> prior runs. Verified on the idle rig: three nodes read `RUNNING`
> (`Start_Container` → `MY START_Container` → `Wait for Time`) with nothing
> happening and zero frames captured. Gating on it would poll `/sequence/json`
> at 30 s indefinitely — ~24 MB/day, erasing the saving — and
> `binary_sensor.sequence_running` would read `on` permanently, which the
> meridian blueprint uses as a condition.

**Container `Iterations` is *completed* iterations** — `0` on a running
container, `42` on a finished loop. Not a progress numerator.

`SEQUENCE-FINISHED` does fire, once, at session end (§3.4). It cannot bound a
session *start*, but it is a valid signal to drop the sequence tier back to the
5-minute interval immediately rather than waiting for the activity heuristic to
go quiet. It must clear the recent-`IMAGE-SAVE` mark as well as the cadence:
that arm is what holds the tier at 30 s for five minutes after the last frame,
so leaving it set means the event buys one tick and nothing more. The two live
arms — a rising count, a camera still exposing — still override it on the next
tick, which is what keeps this a cadence change rather than a latch.

An endpoint that answers **404, 405 or 501 is latched as not served** — a build
without the livestack plugin, or a route this API version does not carry. It is
logged once at INFO and never polled again for the life of the entry, and its
model stays at the empty value so the entities read "nothing here" rather than
going unavailable. A transient failure on a non-fast tier keeps the last model
and retries when the tier is next due; only the fast tier decides availability.

### 6.3 Push path

**The push path calls `async_set_updated_data`, not `async_request_refresh`.**
This single line is what makes the design push-first rather than
socket-as-a-hint.

**A push publishes only while the last poll succeeded.**
`async_set_updated_data` sets `last_update_success`, so an ungated push would
report eleven devices available on a rig that is still unreachable. The fold
accumulates either way and the next successful poll publishes what piled up.

**The §6.4 immediate refetch is requested AFTER that publish**, and the order is
load-bearing: `async_set_updated_data` cancels the debouncer, so publishing
second would eat the refetch the event had just asked for. Publishing also
restarts the fast tier's interval, so a night's ~600 events push the next tick
out by up to 10 s apiece — bounded, and an arriving event *is* the fresher
information that tick would have gone to fetch.

**Reconnect and setup:** replay `/event-history`, dedupe against a
**per-generation** high-water mark by `(Event, Time)`, and cap the fold. A
reconnect POLLS BEFORE IT REPLAYS — N.I.N.A. may have restarted while the socket
was down, and replaying under the stale generation would tag every replayed
event to be filtered straight back out of the fold. That poll carries the
one-shot `?all=true` reseed.

**`IMAGE-SAVE` cannot be deduplicated across the two paths.** The socket sends
it with no `Time` (it is stamped from the frame's own `Date`) and
`/event-history` stores it with the rig's, so a reconnect can leave two copies
of one save in the event set. Nothing may COUNT events: frames are counted, on
`(Date, Filename)`; events are read only as signals.

> *Rationale.* A restart resets `/event-history` with fresh timestamps that can
> be *earlier* than a retained mark — a next-evening restart produces 21:00
> events against an 05:30 mark, and every replayed event would be filtered as
> already-seen. Scoping the mark to the generation makes it correct for free.

`WebSocketV2.Events` is an unbounded `static` list with no cap, eviction or
pagination; it grows for the life of the N.I.N.A. process.

### 6.4 Other

**`PARALLEL_UPDATES`** — `0` on read-only platforms, `1` on command platforms.
This constrains *entity* calls only; the 37 services are unaffected, so a script
calling three `nina.mount_*` services still fires concurrently.

**Image scale derives from the frame's own `FocalLength`**, carried per frame by
`/image-history`, with `CameraInfo.PixelSize` from the fast tier. More correct
than the active profile — it is the focal length in force for *that* frame — and
it needs no availability special case.

**Nothing safety-related is on the floor.** Safety monitor, all weather
channels, dome shutter, mount park state and camera temperature are on the 10 s
fast tier with `SAFETY-CHANGED` on top.

**Weather channels are telemetry, not an abort authority.** A forecast-backed
`ObservingConditions` source (OpenMeteo is a 10-minute-refresh gridded forecast)
must not drive an abort: it reads 0% cloud while you sit under a cloud. Abort
belongs to `binary_sensor.safety_is_safe`. Stated in README and in the blueprint
docs.

## 7. Errors and availability

### 7.1 Taxonomy

`api/errors.py` subclasses **builtins only** — never `HomeAssistantError` — so
the fast suite stays HA-free. Mapping happens in `__init__.py` and
`coordinator.py`.

| Exception | Raised when | Retryable |
|---|---|---|
| `NinaConnectionError` | socket refused, DNS, timeout | yes |
| `NinaUnavailableError` | envelope 5xx, or N.I.N.A. mid-boot | yes |
| `NinaEndpointError` | capability not served by this build | **no** |
| `NinaRequestError` | malformed request (pre-handler 4xx, HTML body) | **no** |
| `NinaCommandError` | envelope `StatusCode` 4xx/5xx with a real `Error` | depends |

**Definitions are semantic, not HTTP.** The status-code mapping is documented
inside `v2/client.py`, which keys on the **envelope's** `StatusCode` except for
genuine EmbedIO routing failures, and handles a **zero-length 200**.

**"No data yet" is not an exception.** `Index out of range` and
`"Sequence is not initialized"` are normalized to `None` / `[]` in
`v2/client.py` — both are ordinary states every time Home Assistant starts
before the observatory.

**The envelope's status code alone cannot classify a failure.** From source,
`"Sequence is not initialized"` is raised by ten guards across nine routes with
**two different codes for the identical condition** — `409` on
`/sequence/{json,state,start,stop,reset,set-target,skip}` and **`400`** on
`/sequence/{edit,load}`. So an envelope `400` may be transient, while a
*pre-handler* 400 (EmbedIO, HTML body) is permanent. `v2/client.py` classifies
on the pair (`StatusCode`, `Error`), never on the code alone, and the
`"is not initialized"` case is recognised by message.

> The OpenAPI document calls this `"Sequencer not initialized"`. The wire says
> `"Sequence is not initialized"`. Match on the source string.

The `Success: false` discrimination stays in `v2/client.py`; §3.5 names the
seven handlers that produce it on success.

### 7.2 Mapping to Home Assistant

- **Setup** (Bronze `test-before-setup`): `NinaEndpointError` →
  `ConfigEntryError`; connection/unavailable → `ConfigEntryNotReady`.
- **Coordinator**: retryable → `UpdateFailed`; `NinaRequestError` /
  `NinaEndpointError` → log once, keep the previous snapshot.
- **Actions** (Silver `action-exceptions`): `ServiceValidationError` for bad
  input, `HomeAssistantError` for genuine failure — platform actions included.

### 7.3 Availability, three levels

1. Cannot reach N.I.N.A. → coordinator fails → all entities unavailable.
2. Device `Connected: false`, or `*-DISCONNECTED` arrived → that device's
   entities unavailable. **Exception:** `binary_sensor.safety_monitor_connected`
   is retained as a diagnostic so the fail-safe trigger set in §5.2.1 works.
   This is not an availability exemption for `safety_is_safe`.
   A weather channel the active source cannot provide is also unavailable
   (§5.2.2).
3. Reachable and connected but the value is missing or sentinel — `"NaN"`,
   a calibration frame's `HFR`/`Stars` (keyed on `ImageType`; `HFR 0` is a
   secondary null-out inside lights, §3.4), empty history, the meridian 24
   sentinel → **`unknown`**.

**`log-when-unavailable`**: transition logged once at `warning`, recovery once
at `info`. `poll_all`'s `except: results[key] = {}` disappears.

### 8.1 Layout and invocation

```
tests/
├── unit/     no HA import — pytest tests/unit -p no:homeassistant
├── ha/       pytest tests/ha        (pytest-homeassistant-custom-component)
├── fixtures/    captured · redacted · authoritative about the wire
├── synthetic/   constructed · authoritative about nothing but our own branches
└── scenarios/   ordered multi-step states (§8.4)
```

`testpaths` is dropped from `pyproject.toml` so a bare `pytest` cannot silently
mix the suites. Dependencies are uv dependency groups: `test` stays lean, PHACC
goes in `test-ha`, **pinned exactly** — it releases near-daily and
hard-pins `homeassistant==2026.9.0`, `pytest==9.0.3`, `pytest-asyncio==1.4.0`,
`syrupy==6.0.0`. No Python or HA matrix; `hacs.json` declares min-HA
**2026.9.0** (D-13).

**`requires-python` is `>=3.14.2`, not `>=3.14`.** uv resolves every dependency
group at lock time, so `homeassistant==2026.9.0`'s patch-level floor applies
even when only the lean group is installed; a bare `>=3.14` makes the lockfile
unsatisfiable. The same single-lockfile behaviour means `test-ha`'s
`pytest==9.0.3` pin governs both suites, which is desirable — they run the same
pytest.

**The seam guard is static, not runtime.** PHACC registers a `pytest11` entry
point named `homeassistant` whose module imports Home Assistant 22 times at
import scope, and pytest loads entry points before collection — so
`"homeassistant" not in sys.modules` fails unconditionally once PHACC is
installed. Instead, AST-walk the seam (`api/`, `derive.py`, `polling.py`,
`session.py`, `const.py`) plus the transitive closure of its first-party
imports and assert no `homeassistant` import. `-p no:homeassistant` on the
unit run makes the runtime check meaningful as a secondary.

Test through **public Home Assistant interfaces**: set up via
`hass.config_entries.async_setup`, assert via `hass.states`, `hass.services`,

One behaviour per test. No tests exercising the standard library or third-party

### 8.3 Fixtures

Captured, never hand-written, via `scripts/capture_fixtures.py`:

```
scripts/capture_fixtures.py --host H --port 1888 --state <slug> [--dry-run]
  → tests/fixtures/<state-slug>_<endpoint-slug>.json, containing the raw envelope
  → re-running against an unchanged rig state produces a byte-identical file
```

**Redaction rules live in one module** (`tests/redaction.py`), imported by both
the capture script and the guard so they cannot drift. Matching is
**case-insensitive**.

| Pattern | Action |
|---|---|
| `*key`, `*token`, `*secret`, `*password`, `*credential` (any casing of "API") | `"REDACTED"` |
| `*path`, `*folder`, `*directory`, `*host`, `*url` | `"REDACTED"` |
| Windows path, bare IPv4, UUID, HA entity id | `"REDACTED"` |
| `DeviceId`, `EntityId` | stable pseudonym `device-<8 hex>`, preserving distinctness |
| device `Name` / `DisplayName` / `Description` matching a site or facility identifier | generic label |
| `TelescopeName`, `CameraName` | `"Telescope"`, `"Camera"` |
| `Filename` | stable pseudonym `frame_<8 hex>.fits`, hashed from the original |
| `TargetName` | keep — an astronomical object |
| `SiteLatitude`, `SiteLongitude`, `SiteElevation`, `Altitude`, `SiderealTime`, `SideOfPier` | **keep** |

**Redaction preserves JSON type, containers included.** A redacted string
becomes `"REDACTED"`, a number `0`, a `null` stays `null`, and a dict stays a
dict — otherwise the type-aware drift guard checks the redactor's output rather
than N.I.N.A.'s, and a settings subtree under a key matching `*Path` collapses
to a string.

**Site coordinates are kept.** The rig is hosted at a public commercial facility,
zeroing them was ineffective anyway (`Altitude` at `Dec 90` *is* the latitude,
and `SiderealTime` against `UtcNow` gives the longitude), and `SiderealTime` and
`SideOfPier` are the inputs §11's maths is verified against. `Filename` is
pseudonymised by **hashing the original**, not numbered by position: frame
identity is `(Date, Filename)` and the fold spans fixtures, so positional
numbering collides distinct frames and splits identical ones — which would make
§8.7's path-equivalence property untestable.

**The guard is a pre-commit hook**, with CI as backstop. CI fires after the push,
by which time a leaked credential is permanent.

> *Rationale.* A trial capture of `/profile/show?active=true` contained a live
> `WeatherUndergroundAPIKey`. A later scan of already-written fixtures found a
> hosting-facility building name, a Home Assistant instance UUID, and 24
> occurrences of HA entity ids that the first rule set had missed.

**`/profile/show` is captured as an allowlist projection**, not excluded and not
denylisted — only `TelescopeSettings.FocalLength`,
`FocuserSettings.{AutoFocusTimeoutSeconds,RSquaredThreshold}`,
`MeridianFlipSettings.*`, `CameraSettings.PixelSize`. It is still polled (§6.1)
and §4.4 and §11 both consume it, so excluding it would leave a polled endpoint
with no fixture, no drift coverage and no mapper test.

`tests/fixtures/README.md` is the state → filename inventory.

### 8.5 The drift guard

Two tests, over the **whole corpus** — not one fixture, or the rule is wrong:
a disconnected device does not null its fields, it drops them (the connected
Mount carries 51 keys, the disconnected 37 — §3.2).

```
test_waivers_state_the_observed_wire_type()      ("deviate only where recorded")
    extract observed types per dotted path from every fixture; for every entry
    in tests/spec_deviations.json (committed, one entry per §3.2 row with the
    wire truth and a reason) whose wire is not "absent", require
    "|".join(sorted(observed[path])) == entry["wire"] — a waiver can neither
    under- nor over-describe the deviation it excuses. Companions fail on a
    stale waiver naming a path the corpus no longer shows and on an "absent"
    waiver whose field appears. Not a type checker run over the generated
    TypedDict output — that output cannot be checked against runtime data
    without a third-party runtime validator; a NEW deviation surfaces through
    the snapshot below.
test_observed_wire_shape_matches_snapshot()
    emit {"Mount.TrackingMode": "str", …} per dotted path, namespaced by the
    endpoint each fixture came from; syrupy it.
```

`"NaN"` is pre-passed to a sentinel marker so nineteen fields do not register as
type errors and drown the signal. The generated file is never hand-edited.

> *Rationale.* Fixtures are ground truth and generated types are known wrong in
> ~15 places, so a naive comparison is red on its first run and gets muted. The
> waiver file is the honest record; the second test is what makes "spec drift per
> release" a reviewable diff, because it fires when the **wire** changes — which
> the spec cannot tell you.

Request parameter names are not generated and are pinned by live-probe tests
(§3.2).

### 8.6 Snapshots

The **entity registry** is the rename artifact — `unique_id`, `entity_id`,
`original_name`, `entity_category`, `entity_registry_enabled_default`. Not
`hass.states`: the disabled long tail has no state, so a state snapshot omits
exactly the entities most likely to be misconfigured. Keep a small separate
state snapshot for value contracts.

One `.ambr` per platform. `HomeAssistantSnapshotExtension`. Sort by `unique_id`.
**Snapshot regeneration is its own commit** — with ~172 entities the diff *is* the
review. Its job here is review, not regression: a changed `unique_id` is not a
bug, it just has to be seen.

Each phase-C PR appends its renames to `docs/2.0-renames.md`. Phase D formats
that file; it does not reconstruct it.

### 8.7 Properties and coverage

Three properties on `session.py`, sampling from the 122 real captured frames so
every generated input is real wire data:

1. **Idempotence** — `fold(f + f) == fold(f)`
2. **Order-independence** — over `st.permutations`
3. **Path-equivalence** — the same frame via `IMAGE-SAVE`, `/image-history` and
   replay folds to one entry

Hypothesis profile `max_examples=50, deadline=None, derandomize=True`.
Everything else stays example-based.

Coverage floors, read from `coverage json` in CI since coverage.py has no
per-file threshold:

```python
FLOORS = {"derive.py": 95, "polling.py": 95, "session.py": 95,
          "api/v2/mapper.py": 90, "config_flow.py": 100}
PENDING: dict[str, int] = {}        # B7 promoted the last entry
```

`branch = true` — Bronze's config-flow rule is about error recovery and the
duplicate-entry guard, both branches. `parallel = true` + `coverage combine`
across the two invocations. No global gate. A floor for a module a later phase
creates sits in `PENDING` and prints a warning: a required job that is knowingly
red for two phases trains everyone to ignore it. B7 promotes `config_flow.py`
into `FLOORS`; D5 asserts `PENDING` is empty.

`FakeNinaClient` gets a conformance test comparing its signatures to
`NinaClientV2`'s, and the HA suite uses a **fixture-backed transport stub** for
`aiohttp` where it needs the real client's envelope logic exercised.

Fixtures carry `_meta: {captured_at, nina_version, api_version, endpoint,
params}`, stripped before type-checking.

### 8.8 Flake sources designed out

`pytest-socket` is active under PHACC and neither `requests_mock` nor `respx`
mocks aiohttp. Do not run the HA suite under `-n auto`. Anything driven by the
push path needs `await hass.async_block_till_done()` after firing, since

## 11. Meridian flip

```
HoursToMeridian    = (RA_JNOW − LST) mod 12
TimeToMeridianFlip = HoursToMeridian + MaxMinutesAfterMeridian
                     [+12 h when UseSideOfPier and already flipped]
```

Verified: LST 21.021944, RA 22.071111 → `(RA−LST) mod 12 = 01:02:57`, matching
`HoursToMeridianString` to the second; the delta is 15.00 min, exactly the
profile's `MaxMinutesAfterMeridian: 15`.

1. **The flip fires when `TimeToMeridianFlip` reaches `(Max − Min)`** — 10
   minutes here, **not zero**. `meridian_flip_warning.yaml`'s `below: 10`
   therefore warns *at* the flip. The correct threshold is
   `warning_minutes + (Max − Min)`, and since both are per-profile a bare
   numeric threshold is not portable between rigs. Phase D uses
   `MOUNT-BEFORE-FLIP`.
2. **The 24 sentinel is returned when `TrackingEnabled == false`** — parked,
   homed, or simply tracking off. The mapper nulls the **literal** `24` and any
   value while tracking is off, nothing more: **12 h is legitimate**, meaning
   "just flipped", and so is **24.08** — a `UseSideOfPier` rig reads a few
   minutes over 24 for up to `MaxMinutesAfterMeridian` after its flip. Neither
   "≥12" nor "≥24" is the rule.
3. `double.NaN` when the mount object is null.

The `Meridian Flip_Trigger` node carries its **own** `MinutesAfterMeridian` /
`MaxMinutesAfterMeridian` / `UseSideOfPier` — on the **`/sequence/state`**
trigger node, which §6.1 does not poll. `/sequence/json`'s node carries only
`TimeToFlip`, which passes through `SequenceNode.attributes` raw, `24` sentinel
included (phase C's sequence platform nulls it). Phases C and D therefore take
`Min`/`Max`/`UseSideOfPier` from `/profile/show` `MeridianFlipSettings`; they
matched the trigger's on this rig.
