# 2.0 entity renames

Every entity whose `entity_id` or `unique_id` changed in 2.0, with the 1.4.5
name it replaces, plus the config entry and options changes. Appended by each
phase-B and phase-C PR; formatted in D1.

The authoritative record is the entity registry snapshot (§8.6) — this file must
match it. **That snapshot does not exist yet**: the only `.ambr` in the tree is
`tests/unit/__snapshots__/test_drift_guard.ambr`, which is the API drift guard,
not the registry. Until phase C writes one, the rows below are checked against
the code and the HA tests directly.

Scope so far: **phases A and B, plus C1 (`binary_sensor`)**. The remaining 1.4.5
platforms are unregistered until phase C migrates them, so an entity missing
today is not necessarily removed and gets no row here until its phase records
one.

**An upgrade does not rename anything on its own.** Home Assistant keys the
registry on `unique_id`, and a row whose `unique_id` is unchanged keeps the
`entity_id` it was minted with, whatever device it moves to. The "2.0" column is
therefore what a **fresh** install generates; an existing install keeps its
1.4.5 `entity_id` (and its dashboards and automations keep working) until the
user renames the entity themselves.

`<instance>` is the instance name from the config flow, slugified — `N.I.N.A.`
by default, which slugifies to `n_i_n_a`. The 1.4.5 ids are what a 1.4.5 install
mints under Home Assistant 2026.9, which builds every entity id from area,
device and entity name — so the device name 1.4.5 hardcoded, `N.I.N.A.
Astrophotography`, is part of them. A user who installed 1.4.5 under an earlier
Home Assistant, before entity ids carried the device name, has the unprefixed
ids 1.4.5's README documents (`light.flat_panel_light`). Either way an upgrade
leaves them as they are.

The 2.0 ids likewise assume **no area is assigned when the entity is first
registered**: area is the first of Home Assistant's default id parts, so an
entity minted into an area carries the area name ahead of the device name.

## Entities

| 1.4.5 | 2.0 | Why |
|---|---|---|
| `light.n_i_n_a_astrophotography_flat_panel_light` | `light.<instance>_flat_panel_light` | The panel is its own device, `"<instance> Flat Panel"` (§5.1), so the id is built from that device name plus the entity name `Light`. `unique_id` is **unchanged** at `{entry_id}_flat_panel_light`. |
| `switch.n_i_n_a_astrophotography_flat_panel_light` | removed | One entity per device function (§5.3.4): the panel's light was both a `light` and a `switch`; the `light` survives. Its `unique_id` was `{entry_id}_flat_light_switch`, which nothing in 2.0 claims, so an upgraded install keeps the row as an unavailable leftover until it is deleted. |

## Entities — `binary_sensor` (C1)

1.4.5 shipped twenty binary sensors; 2.0 ships fourteen. Seven of the twenty
survive and thirteen are removed. Twelve of those thirteen are on the design's
cut list; the thirteenth, `mount_slewing`, is a 1.4.5-only cut. The cut list's
remaining eight — `rotator_connected`, `switch_connected`,
`camera_dew_heater_on`, `dome_following`, `rotator_reversed`,
`flatdevice_cover_open`, `flatdevice_light_on`, `livestack_running` — exist only
on `wip/v2.0`, which never shipped, so they have nothing to rename from and get
no row.

**Four survivors change `unique_id`**, which Home Assistant cannot follow: a
fresh entity is minted and the 1.4.5 row is left behind as an unavailable
leftover until the user deletes it. They are marked below.

| `binary_sensor.n_i_n_a_astrophotography_camera_connected` | removed | Availability (§5.2.1). A disconnected camera makes its entities `unavailable`, which is observable in automations. |

| `binary_sensor.n_i_n_a_astrophotography_focuser_connected` | removed | Availability (§5.2.1). |

## Configuration

| 1.4.5 | 2.0 | Why |
|---|---|---|
| entry title `N.I.N.A. <version> @ <host>` | entry title is the instance name | The version in a title goes stale on the rig's next update, and the title is what names the hub device. |
| — | entry data `instance_name`, required in the add form, default `N.I.N.A.` | Multi-rig (§5.1): the hub device is named `"<instance>"` and every equipment device `"<instance> <Kind>"`. An entry created before 2.0 carries no `instance_name` and falls back to its entry title. A blank name is refused — it would title the entry `""` and name devices `" Camera"` — and so is one another entry already uses, which would name two rigs' devices alike. |
| entry data `api_version`, a `v2`-only dropdown | the dropdown is gone | It only ever offered one value. The key is still read from existing entry data by the legacy client that serves the unmigrated services; phase C retires both. |
| — | options `rollover_hour`, 0–23, default 12 | Where the session boundary falls (§4.4). Noon local is the astronomical night's natural break; a rig west of the meridian on UTC needs to move it. |
| `poll_interval` 5–300 s, in both the add and the options form | 5–60 s, in both | **Breaking.** The tiering design (§6.1) assumes a fast tier near 10 s; a 300 s poll defeats it. A value above 60 already stored on an entry keeps polling at that rate — nothing rewrites it — and has to be lowered to 60 or less the next time the options form is submitted. |
| — | the hub device carries a `configuration_url` of `http://<host>:<port>` | The rig's own web UI, one click from the device page. |
