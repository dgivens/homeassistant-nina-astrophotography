# 2.0 entity renames

Every entity whose `entity_id` or `unique_id` changed in 2.0, with the 1.4.5
name it replaces, plus the config entry and options changes. Appended by each
phase-B and phase-C PR; formatted in D1.

The authoritative record is the entity registry snapshot (§8.6) — this file must
match it. **That snapshot does not exist yet**: the only `.ambr` in the tree is
`tests/unit/__snapshots__/test_drift_guard.ambr`, which is the API drift guard,
not the registry. Until phase C writes one, the rows below are checked against
the code and the HA tests directly.

Scope so far: **phases A and B, plus C1 (`binary_sensor`), C7 (the
`sensor` session family and weather channels) and C2 (`number` and
`select`)**. The remaining 1.4.5
platforms are unregistered until phase C migrates them, so an entity missing
today is not necessarily removed and gets no row here until its phase records
one.

**An upgrade does not rename anything on its own.** Home Assistant keys the
registry on `unique_id`, and a row whose `unique_id` is unchanged keeps the
`entity_id` it was minted with, whatever device it moves to. The "2.0" column is
therefore what a **fresh** install generates; an existing install keeps its
1.4.5 `entity_id` (and its dashboards and automations keep working) until the
user renames the entity themselves.

`<instance>` is the instance name from the config flow, slugified — `N.I.N.A.`
by default, which slugifies to `n_i_n_a`. The 1.4.5 ids are what a 1.4.5 install
mints under Home Assistant 2026.9, which builds every entity id from area,
device and entity name — so the device name 1.4.5 hardcoded, `N.I.N.A.
Astrophotography`, is part of them. A user who installed 1.4.5 under an earlier
Home Assistant, before entity ids carried the device name, has the unprefixed
ids 1.4.5's README documents (`light.flat_panel_light`). Either way an upgrade
leaves them as they are.

The 2.0 ids likewise assume **no area is assigned when the entity is first
registered**: area is the first of Home Assistant's default id parts, so an
entity minted into an area carries the area name ahead of the device name.

## Entities

| 1.4.5 | 2.0 | Why |
|---|---|---|
| `light.n_i_n_a_astrophotography_flat_panel_light` | `light.<instance>_flat_panel_light` | The panel is its own device, `"<instance> Flat Panel"` (§5.1), so the id is built from that device name plus the entity name `Light`. `unique_id` is **unchanged** at `{entry_id}_flat_panel_light`. |
| `switch.n_i_n_a_astrophotography_flat_panel_light` | removed | One entity per device function (§5.3.4): the panel's light was both a `light` and a `switch`; the `light` survives. Its `unique_id` was `{entry_id}_flat_light_switch`, which nothing in 2.0 claims, so an upgraded install keeps the row as an unavailable leftover until it is deleted. |

## Entities — `binary_sensor` (C1)

1.4.5 shipped twenty binary sensors; 2.0 ships fourteen. Seven of the twenty
survive and thirteen are removed. Twelve of those thirteen are on the design's
cut list; the thirteenth, `mount_slewing`, is a 1.4.5-only cut. The cut list's
remaining eight — `rotator_connected`, `switch_connected`,
`camera_dew_heater_on`, `dome_following`, `rotator_reversed`,
`flatdevice_cover_open`, `flatdevice_light_on`, `livestack_running` — exist only
on `wip/v2.0`, which never shipped, so they have nothing to rename from and get
no row.

**Every survivor keeps its 1.4.5 `unique_id`**, four of them through a
`unique_id_suffix` on the descriptor because the new `key` reads better than the
old one. An upgraded install therefore keeps its registry rows and its entity
ids, and an automation pointing at the 1.4.5 safety entity keeps working.

## Entities — `sensor`, the session family (C7)

1.4.5 shipped the session and last-image statistics **twice**: a polled family
in `sensor.py` read off `/image-history`, and a pushed family in
`frame_stats_sensor.py` fed by `IMAGE-SAVE`. They disagreed, and the pushed
semantics won by measurement (§5.2.4) — after a dawn flat run the polled
`Last Image HFR` read `0` and `Last Image Mean ADU` read `33139.77`, which is
exactly the last FLAT's mean. **So the survivor keeps the PUSHED entity's
`unique_id`** (`frame_*`) and the polled duplicate is the row that goes.

Twenty-four 1.4.5 sensors collapse to thirteen hub entities. Every one of the
thirteen is a survivor: none is new, and none changes its `unique_id`.

| 1.4.5 | 2.0 | Why |
|---|---|---|
| `sensor.n_i_n_a_astrophotography_session_frame_count` | `sensor.<instance>_session_image_count` | `unique_id` **unchanged** at `_frame_session_count`. Counts every frame in the session window, calibration included — "did the flats run?" is a question the lights-only aggregates cannot answer. `light_count` rides along as an attribute. **`state_class` changes** from `total_increasing` to `measurement`: the count resets at the rollover, and a sum across sessions is not what the entity means. |
| `sensor.n_i_n_a_astrophotography_session_integration_time` | `sensor.<instance>_session_integration_time` | `unique_id` **unchanged** at `_frame_session_integration`. **Breaking for statistics:** the unit moves from `min` to `h` and the `state_class` from `total_increasing` to `measurement`, with `device_class: duration` added. Both are HA duration units so the recorder converts, but the statistics type change means the long-term series restarts. |
| `sensor.n_i_n_a_astrophotography_session_avg_hfr` | `sensor.<instance>_session_avg_hfr` | `unique_id` **unchanged** at `_frame_session_avg_hfr`. Now carries the `by_target` and `by_filter` breakdowns as attributes (§4.4): session-wide means are dominated by whichever target got the most frames, and per-target means ranged 1.429–1.667 against a session-wide 1.513. |
| `sensor.n_i_n_a_astrophotography_session_best_hfr` | `sensor.<instance>_session_best_hfr` | `unique_id` **unchanged** at `_frame_session_min_hfr`. |
| `sensor.n_i_n_a_astrophotography_session_worst_hfr` | `sensor.<instance>_session_worst_hfr` | `unique_id` **unchanged** at `_frame_session_max_hfr`. No longer `DIAGNOSTIC` — the three HFR aggregates belong together. |
| `sensor.n_i_n_a_astrophotography_session_avg_stars` | `sensor.<instance>_session_avg_stars` | `unique_id` **unchanged** at `_frame_session_avg_stars`. |
| `sensor.n_i_n_a_astrophotography_last_frame_hfr` | `sensor.<instance>_last_image_hfr` | `unique_id` **unchanged** at `_frame_last_hfr`. Reads the newest LIGHT, never the newest frame. |
| `sensor.n_i_n_a_astrophotography_last_frame_stars` | `sensor.<instance>_last_image_star_count` | `unique_id` **unchanged** at `_frame_last_stars`. |
| `sensor.n_i_n_a_astrophotography_last_frame_mean_adu` | `sensor.<instance>_last_image_mean_adu` | `unique_id` **unchanged** at `_frame_last_mean_adu`. |
| `sensor.n_i_n_a_astrophotography_last_frame_exposure` | `sensor.<instance>_last_image_exposure` | `unique_id` **unchanged** at `_frame_last_exposure`. |
| `sensor.n_i_n_a_astrophotography_last_frame_guide_rms` | `sensor.<instance>_last_image_rms` | `unique_id` **unchanged** at `_frame_last_rms`. Arcseconds, so it is comparable with `sensor.<instance>_guider_rms_total` and across rigs; a total of 0 is no guiding rather than perfect guiding, and is `unknown`. |
| `sensor.n_i_n_a_astrophotography_last_frame_target` | `sensor.<instance>_last_image_target` | `unique_id` **unchanged** at `_frame_last_target`. |
| `sensor.n_i_n_a_astrophotography_last_frame_filter` | `sensor.<instance>_last_image_filter` | `unique_id` **unchanged** at `_frame_last_filter`. |
| `sensor.n_i_n_a_astrophotography_last_image_hfr` | removed | The POLLED duplicate (§5.2.4). It read `0` after a dawn flat run, because the calibration HFR sentinel of zero looks like a measurement. Its `unique_id` was `_image_last_hfr`, which nothing in 2.0 claims. |
| `sensor.n_i_n_a_astrophotography_last_image_star_count` | removed | The polled duplicate; `_image_last_star_count`. It read `unknown`, the `-1` sentinel being caught where the HFR `0` was not. |
| `sensor.n_i_n_a_astrophotography_last_image_mean_adu` | removed | The polled duplicate; `_image_last_mean_adu`. It read the last FLAT's 33,139.77. |
| `sensor.n_i_n_a_astrophotography_session_image_count` | removed | The polled duplicate; `_image_count`. It counted the whole `/image-history` payload, which is process-scoped, not the night. |
| `sensor.n_i_n_a_astrophotography_last_frame_min_adu` | removed | `Frame` carries no `Min`: `api/models.py` is closed to fields nothing above the seam consumes. Same for `_frame_last_max_adu`, `_frame_last_median_adu`, `_frame_last_std_dev_adu` and `_frame_last_hfr_std_dev`. |

| `sensor.n_i_n_a_astrophotography_frame_sparkline_data` | removed | `_frame_sparkline_data` — four series in the attributes of a sensor whose state was the frame count. Phase D's card reads recorder history. |
| — | `sensor.<instance>_session_start` | **New** (§5.4). The most recent rollover in the RIG's local time: 12:00 UTC is 07:00 on a UTC−5 rig, inside its dawn flats. `device_class: timestamp`. |

## Entities — `sensor`, the weather channels (C7)

Thirteen ObservingConditions channels, each keeping its 1.4.5 `unique_id`. What
changes is that they are **created on sight and kept** (§5.2.2) rather than
registered unconditionally, and that they move from the hub to the
`"<instance> Weather"` device — so a **fresh** install's ids carry `weather`
twice over (`sensor.n_i_n_a_weather_sky_brightness`), while an upgraded install
keeps the 1.4.5 ids.

An upgraded install has all thirteen rows in its registry already, so all
thirteen come back at setup, and the ones the active source cannot report read
`unavailable` rather than `unknown`. That is the intended behaviour, not a
regression: 1.4.5 left them at `unknown` forever.

| 1.4.5 | 2.0 | Why |
|---|---|---|
| `sensor.n_i_n_a_astrophotography_weather_temperature` | `sensor.<instance>_weather_temperature` | `unique_id` **unchanged** at `_weather_temperature`. |
| `sensor.n_i_n_a_astrophotography_weather_humidity` | `sensor.<instance>_weather_humidity` | `unique_id` **unchanged**. |
| `sensor.n_i_n_a_astrophotography_dew_point` | `sensor.<instance>_weather_dew_point` | `unique_id` **unchanged** at `_weather_dew_point`. |
| `sensor.n_i_n_a_astrophotography_barometric_pressure` | `sensor.<instance>_weather_pressure` | `unique_id` **unchanged** at `_weather_pressure`. `device_class` moves from `pressure` to `atmospheric_pressure`, which is what an ObservingConditions station reports. |
| `sensor.n_i_n_a_astrophotography_rain_rate` | `sensor.<instance>_weather_rain_rate` | `unique_id` **unchanged** at `_weather_rain_rate`. Gains `device_class: precipitation_intensity`. |
| `sensor.n_i_n_a_astrophotography_cloud_cover` | `sensor.<instance>_weather_cloud_cover` | `unique_id` **unchanged** at `_weather_cloud_cover`. No device class: Home Assistant has none for cloud cover. |
| `sensor.n_i_n_a_astrophotography_sky_brightness` | `sensor.<instance>_weather_sky_brightness` | `unique_id` **unchanged** at `_weather_sky_brightness`. LUX with `device_class: illuminance` — `SkyBrightness` and `SkyQuality` are two distinct ASCOM properties, and the rig reports `SkyBrightness 5692` beside `SkyQuality "NaN"`. |
| `sensor.n_i_n_a_astrophotography_sky_quality` | `sensor.<instance>_weather_sky_quality` | `unique_id` **unchanged** at `_weather_sky_quality`. `mag/arcsec²`, no device class — Home Assistant has none. Neither captured source reports it, so it appears only on a rig that has an SQM. |

| `sensor.n_i_n_a_astrophotography_weather_station_name` | `sensor.<instance>_weather_source` | `unique_id` **unchanged** at `_weather_name`. §5.4 lists `sensor.weather_source` as an addition, but it reports exactly what 1.4.5's station-name sensor reported, so it is a rename and the row survives. ## Entities — `number` and `select` (C2)

1.4.5 shipped seven numbers and two selects. 2.0 ships seven numbers — three of
the 1.4.5 seven, plus four new ones — and the same two selects. **Every survivor
keeps its 1.4.5 `unique_id`**, through a `unique_id_suffix` on the descriptor,
so an upgraded install keeps its registry rows and the automations on them.

The four numbers with no 1.4.5 row — `flat_panel_brightness`,
`camera_usb_limit`, `rotator_mechanical_position` and `dome_azimuth` — are
§5.2.3's survivors of read-only sensors that existed only on `wip/v2.0`, so they
have nothing to rename from. `dome_azimuth` appears only on a rig with a dome
(§5.2.2), and `camera_usb_limit` and `rotator_mechanical_position` ship
`DIAGNOSTIC` and disabled.

| 1.4.5 | 2.0 | Why |
|---|---|---|
| `number.n_i_n_a_astrophotography_camera_gain` | removed | No client method binds gain: `/equipment/camera/set-gain` is not in the 2.0 client, and `models.py` is closed to fields nothing consumes. 1.4.5 reached through `client._get` to send it. |
| `number.n_i_n_a_astrophotography_camera_offset` | removed | As above, for `/equipment/camera/set-offset`. |
| `number.n_i_n_a_astrophotography_camera_binning` | removed | Binning is a mode name (`"1x1"`), not a number: a slider of 1–4 cannot express the `BinningModes` the camera reports, and `set-binning` takes `x` and `y`. |
| `number.n_i_n_a_astrophotography_filter_wheel_slot` | removed | `select.<instance>_filter_wheel_filter` is the survivor: the wheel reports filter NAMES, and a slot number is the same choice with the names thrown away. |
| `number.n_i_n_a_astrophotography_camera_cooling_setpoint` | `number.<instance>_camera_target_temperature` | `unique_id` **unchanged** at `_camera_cooling_setpoint`, via `unique_id_suffix`. Named for `CameraInfo.TargetTemp`, which is what it reads. There is no setpoint endpoint: changing it is a cool-down to the new value. |
| `number.n_i_n_a_astrophotography_focuser_target_position` | `number.<instance>_focuser_position` | `unique_id` **unchanged** at `_focuser_position_control`. Not a *target*: the state is the focuser's ACTUAL position (§5.2.3), so the name no longer claims otherwise. `sensor.<instance>_focuser_position` is reinstated alongside it (C6) for long-term statistics. |
| `number.n_i_n_a_astrophotography_rotator_position` | `number.<instance>_rotator_position` | `unique_id` **unchanged** at `_rotator_position_control`. Sky position angle, meaningful only while `binary_sensor.<instance>_rotator_synced` is on. |
| `select.n_i_n_a_astrophotography_active_filter` | `select.<instance>_filter_wheel_filter` | `unique_id` **unchanged** at `_filterwheel_select`. Options are the wheel's own `AvailableFilters`; 1.4.5's `"—"` placeholder for an empty wheel is gone, since an empty option list is what "no filters" means. |
| `select.n_i_n_a_astrophotography_mount_tracking_rate` | `select.<instance>_mount_tracking_rate` | `unique_id` **unchanged** at `_tracking_rate_select`. Options now come from the mount's `TrackingModes` rather than the full five-value enum — this mount offers four and no King — and the sent `mode` is the API's enum value rather than the position in that list (§5.3.6). 1.4.5 also read a `TrackingRate` field the wire does not send and defaulted to `Sidereal`; the state is `TrackingMode`, and `unknown` when the mount reports none. |

## Configuration

| 1.4.5 | 2.0 | Why |
|---|---|---|
| entry title `N.I.N.A. <version> @ <host>` | entry title is the instance name | The version in a title goes stale on the rig's next update, and the title is what names the hub device. |
| — | entry data `instance_name`, required in the add form, default `N.I.N.A.` | Multi-rig (§5.1): the hub device is named `"<instance>"` and every equipment device `"<instance> <Kind>"`. An entry created before 2.0 carries no `instance_name` and falls back to its entry title. A blank name is refused — it would title the entry `""` and name devices `" Camera"` — and so is one another entry already uses, which would name two rigs' devices alike. |
| entry data `api_version`, a `v2`-only dropdown | the dropdown is gone | It only ever offered one value. The key is still read from existing entry data by the legacy client that serves the unmigrated services; phase C retires both. |
| — | options `rollover_hour`, 0–23, default 12 | Where the session boundary falls (§4.4). Noon local is the astronomical night's natural break; a rig west of the meridian on UTC needs to move it. |
| `poll_interval` 5–300 s, in both the add and the options form | 5–60 s, in both | **Breaking.** The tiering design (§6.1) assumes a fast tier near 10 s; a 300 s poll defeats it. A value above 60 already stored on an entry keeps polling at that rate — nothing rewrites it — and has to be lowered to 60 or less the next time the options form is submitted. |
| — | the hub device carries a `configuration_url` of `http://<host>:<port>` | The rig's own web UI, one click from the device page. |
